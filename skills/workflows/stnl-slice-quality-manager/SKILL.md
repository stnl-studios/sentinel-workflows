# stnl-slice-quality-manager

## Purpose

Run only `VALIDATE_SLICE`. Check deterministic prerequisites, delegate technical validation to the configured independent runner, persist its exact result and per-finding dispositions, and complete the slice in the same operation only when it returns `PASS`.

## Inputs

- `SPEC_PATH`: required for manual launches. A directory must contain `feature_spec.md` and uses its `execution/` child; that file path resolves identically; another requirements file uses sibling `<stem>-execution/`. Block every other form. Managed launches use the cross-checked `STNL_MANAGED_CONTEXT` and mechanical helper variables; never derive paths from a private home or thread name.
- `SLICE`: required and explicit; normalize one unsigned decimal number to `slice-NN` and never infer it.
- For manual launches, use the configured independent runner. When `STNL_RUNNER_ADAPTER` is configured, invoke `node "$STNL_RUNNER_ADAPTER" --operation VALIDATE_SLICE --slice <slice-NN>` with the minimum payload on stdin and retain its absolute `semanticResponseFile` and receipt. Without an adapter or managed context, use a fresh independent native context with no inherited conversation history. Select the installed platform runner when supported (Codex `stnl_validation_runner`, Claude Code `@agent-stnl-validation-runner`). If the native API only spawns an independent generic agent, use `fork_turns:"none"` or its platform equivalent and require that agent, before any scope reads or checks, to read and follow the complete installed runner contract (Codex `~/.codex/agents/stnl_validation_runner.toml` `developer_instructions`; Claude Code `~/.claude/agents/stnl-validation-runner.md` body). Require the installed file to identify `stnl-validation-runner` and contain its canonical contract marker; a missing, malformed, or different runner contract blocks. Give it the official preflight identity and minimum operation payload, instruct it to follow the contract's no-write rule, and save its one raw JSON response in an absolute temporary file outside the SPEC. Identify this as a contract-loaded independent agent, not a selected registered runner type. Reading `developer_instructions` from a file is task-level instruction loading; it does not confer developer-level priority or the enforcement guarantee of a registered agent. If independent spawning or exact contract loading is unavailable, block; a generic agent without that contract is not the runner. Managed launches use the pathless bridge below. The human launcher supplies no helper path or benchmark sequence.

## Authority

The configured independent runner owns the technical verdict. This skill owns semantic finding records and dispositions in the selected task file and, only after `PASS` prerequisites succeed, the selected row in `tasks.md`. It does not edit requirements, plans, code, tests, or divergences. Derive the canonical workspace from the official `SPEC_PATH` and its Git root. Create the isolated `CANDIDATE_EXECUTION_ROOT` through this skill's `node "<SKILL_ROOT>/runtime/prepare-validation-copy.mjs" --spec-path <SPEC_PATH> --slice <slice-NN> --candidate-parent <TMPDIR>` before semantic edits; use the returned exact path. The helper verifies a byte-identical complete copy of the live execution tree outside SPEC and execution roots. For `VALIDATE_SLICE`, the independent runner returns one raw JSON object with exactly the model-owned semantic keys `status`, `head`, `commands`, `evidence`, `findingReferences`, `findingDispositions`, `blockers`, `unexpectedWorkspaceEffects`, and `persistenceSummary`; it does not emit paths, hashes, records, or mechanically derived `Type` or `Operation` fields. In managed/adapter mode, `commands` are non-authoritative claims and marked SDK command events supply exact commands and observed exits. In native mode, the runner actually executes checks and reports literal commands and observed numeric exits; the preparer records these runner-reported values without claiming mechanical capture. Discovery commands are unmarked. The main context saves the JSON unchanged and makes only semantic edits to finding records/dispositions and the final diff summary in the isolated candidate; it must leave `Validation Attempts`, `Effective Validation Base`, `Final Result`, and the selected `tasks.md` row identical to live authority. It then invokes the deterministic `prepare-validation-candidate.mjs` once before strict candidate validation. This boundary reuses the existing execution-state authority and runner-evidence serializer to derive the next attempt ID and type, canonical scope and physical targets from `Changed Areas` and `Prior Validation Overlap`, official preflight command, task-relative `path.relative`, normalized separators, and complete SHA-256 values. It serializes and writes the full attempt; only for `PASS` does it also write the complete Effective Validation Base, `Final Result: PASS`, and the selected `tasks.md` PASS row. `NEEDS_FIX` and `BLOCKED` append only their attempt, leaving base, final result, and row unchanged. The strict candidate validator remains mandatory and authoritative. On rejection, preserve that candidate and its exact diagnostic. If the cause is a correctable semantic or serialization defect and official preflight still authorizes the same operation on unchanged live authority, create a fresh byte-identical copy from live, apply the diagnosed correction there, and run the preparer once for that new candidate before strict validation. Never rewrite or republish the rejected candidate, change the runner's semantic response, or use a phrase-based rejection detector.

In native mode, save the independent runner's raw final JSON response unchanged to the absolute temporary semantic response file. In managed/adapter mode the adapter owns capture: pass its absolute semantic response file byte-for-byte to the candidate preparer and do not invoke a second capture. If it returns only structured JSONL output, resolve the capture helper from the `stnl-slice-executor` sibling in this same bundle: `<EXECUTOR_SKILL_ROOT> = path.resolve(SKILL_ROOT, "../stnl-slice-executor")`. Execute `node "<EXECUTOR_SKILL_ROOT>/runtime/capture-runner-response.mjs" --structured-output-file <absolute-runner-output> --output <absolute-temp-file>`; the helper is not owned by this quality-manager runtime. The preparer accepts the semantic file and performs deterministic candidate serialization before candidate validation.
For `VALIDATE_SLICE`, the runner does not invoke separate `--record`, `--manifest`, `--response`, or `--validation-bundle` commands. The main context uses only the deterministic `prepare-validation-candidate.mjs` boundary after the runner returns. A candidate is incomplete and cannot be validated until the preparer has written the canonical attempt and, for `PASS`, the complete base and terminal fields.

If managed/adapter preparation returns `RUNNER_RESULT_BLOCKED` with a bound receipt, strictly validate and publish that blocker candidate, then read back `MANDATORY_RECOVERY`; never report the preparer return alone as recovery. If an already prepared PASS candidate is rejected by the strict validator for the structured `PASS_COMMAND_EXIT_NONZERO` violation on the new selected attempt, preserve it and use `runtime/recover-rejected-validation-candidate.mjs` only with the matching managed/adapter receipt and bound events. Any native rejection lacks that receipt-bound recovery: preserve its candidate and diagnostic and block publication. A resumed runner must diagnose the failed check and produce new pertinent evidence or the correct non-PASS classification; neither a later green check nor a semantic PASS erases the earlier failed event.

Execution preflight is read-only. An accepted mandatory resume includes a structured `MANDATORY_RECOVERY` record; an incompatible request includes structured `RECOVERY_TARGETS`. Preserve those fields exactly. Only when preflight reports a mechanical violation for the exact `Findings IDs` alias or the exact historical `Check discovery sources` / `Check discovery actions` pair may this skill explicitly run `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --repair-known-contract` once and repeat the original preflight; every other contract violation blocks.

## Minimum Reads

- `tasks.md`, selected detailed plan and task file, referenced requirements;
- `references/validation-base.md` before persisting a result;
- local `references/execution-record-schema.md` before interpreting or changing findings, divergences, attempts, or terminal state;
- Implementation Test Evidence and Findings Test Evidence for the selected slice;
- only artifacts needed for cheap prerequisites and faithful persistence.

## VALIDATE_SLICE

When `STNL_MANAGED_CONTEXT` is present, treat its cross-checked shell variables as the only mechanical path, operation, and slice transport for this operation. In every later helper command use `"$STNL_MANAGED_SPEC_PATH"`, `"$STNL_MANAGED_WORKSPACE"`, and `"$STNL_MANAGED_SLICE"` where the command needs those arguments. Do not copy a path from the launcher, private skill installation, `CODEX_HOME`, a previous output, or memory into a new command. Execute pathless `node "$STNL_MANAGED_PREFLIGHT"`; then invoke pathless `node "$STNL_MANAGED_RUNNER_BRIDGE" --payload-file "$STNL_MANAGED_RUNNER_PAYLOAD"` with only the semantic payload. Do not copy the current adapter, snapshot, bridge, preflight, `SPEC_PATH`, workspace, operation, slice, execution root, plan/task path, or authority identity into top-level semantic runner fields or envelope assignments. The adapter supplies that envelope mechanically. Nested semantic references such as `overlap.slice` may identify historical work; they cannot replace the current envelope or authorize paths. If the managed context is absent, use the manual launcher `SPEC_PATH` and normal preflight below. Any disagreement between explicit input and managed context blocks in runtime before dispatch or publication.

Before content reads or delegation, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> VALIDATE_SLICE <SLICE>` for manual launches. Managed `VALIDATE_SLICE` executes pathless `node "$STNL_MANAGED_PREFLIGHT"`, which reads the context and checks current fingerprint, state, legal operation/slice, adapter agreement, and snapshot-owned runtime identity deterministically. Its state-derived recovery target is authority: when it blocks, preserve the exact concrete legal operation and slice instead of inferring either from the current request. Require all artifacts, matching current requirements fingerprint and plan revision, completed serial dependencies and mandatory checklist, no active blocking divergence, an open non-superseded slice, and valid check/attempt/finding/blocker structure. A normally consistent `IMPLEMENTED_AWAITING_VALIDATION`, `FINDINGS_CORRECTED`, `VALIDATION_BLOCKED`, `IMPLEMENTATION_RETRY_EXHAUSTED`, or `FINDINGS_RETRY_EXHAUSTED` permits this operation. If terminal implementation evidence is paired with an incomplete mandatory checklist, validation remains blocked even when the observed state has one of those names: preserve the runtime's exact mandatory `stnl-slice-executor / EXECUTE_SLICE / slice-NN` recovery target. After that slice becomes complete, normal validation authority returns without manual lifecycle edits. `VALIDATION_NEEDS_FIX` first requires `APPLY_FINDINGS`. The first invocation is `initial`; every later invocation is `revalidation`, including after `BLOCKED`. A terminal `PASS` or `SUPERSEDED` slice is immutable. Block before invoking the runner when any condition fails.

Determine from the current global plan and serial task rows whether this is the last open effective slice whose `PASS` would make the current revision terminal. For an intermediate slice, keep validation scoped to that slice and its relevant overlaps. For the last open slice, the same formal validation also owns the terminal semantic review: send the global plan and serial order, compact summaries and final results of earlier slices, their pertinent Effective Validation Bases, current requirements authority, coverage and reconciliation evidence, and only the overlap or integration risks needed to judge the combined delivery. Do not send complete history or every artifact by default.

The runner must then assess global requirements coverage, reconciliation against current authority, cross-slice consistency, and whether required integration or stabilization work is missing from the materialized strategy. A locally valid final slice is not sufficient for terminal `PASS`. Missing authority, strategy, or unmaterialized integration work is formal `BLOCKED` with the concrete cause and an explicit `REPLAN` handoff; do not invent a terminal PASS, a new operation, another attempt, or an automatic integration slice.

The main context does not rerun tests, redo validation, soften findings, promote `BLOCKED`, or emit another technical verdict.

Prior test evidence is auxiliary, never a formal verdict. Pass it to the runner with the selected diff and scope. The runner independently checks whether the tested file state is still current, the commands were authoritative, selection and coverage remain sufficient, new risks appeared, and prior-slice overlaps require additional regressions. It must independently review a prior `TESTS_NOT_APPLICABLE`: confirm which read-only discovery actions were performed, which discovery sources were consulted, which verification types were considered, and whether any applicable verification command was omitted; reject it when absence of a tool or environment was confused with absence of applicability, and perform proportional static inspection or executable verification when needed. It may reuse current adequate evidence to avoid unjustified repetition, but executes or repeats checks proportionally when state, authority, coverage, or risk requires it. Neither `TESTS_PASS` nor `TESTS_NOT_APPLICABLE` reduces the formal requirements below an independent verdict, creates a Validation Attempt or Effective Validation Base before `VALIDATE_SLICE`, or guarantees `PASS`.

Start validation in a new independent delegated session with no inherited conversation history. In managed mode use only `node "$STNL_MANAGED_RUNNER_BRIDGE" --payload-file "$STNL_MANAGED_RUNNER_PAYLOAD"`; native delegation cannot replace its broker or receipt. In native mode use the installed named runner or the contract-loaded independent agent described in Inputs; that agent performs checks and the independent verdict under the complete installed runner contract while the main context runs no verification. Pass compact implementation/findings evidence, finding and attempt summaries, changed scope and diff, overlaps, bounded terminal context only for the last open slice, and strictly necessary context. Require the runner to account for every applicable acceptance criterion against concrete current implementation and check evidence; a passing test count alone does not establish coverage. Judge the pre-publication task state: the preparer writes the new Validation Attempt and, on PASS, Effective Validation Base, Final Result, and global row only after the runner verdict. Their pending state before that verdict is not a blocker. In managed/adapter mode do not repeat the current operation, `SPEC_PATH`, workspace, execution root, slice, plan/task paths, requirements authority, snapshot, adapter, bridge, or preflight identity in top-level semantic fields or envelope assignments; the verified adapter envelope owns them. Historical overlap references remain semantic context and grant no path authority. In native mode include the official preflight's operation, slice, authority and concrete canonical SPEC/workspace/plan/task paths in the handoff. Resolve those paths from the manual launcher and official preflight, never private-home identity or a candidate path. Never send conversation history or full logs.

Classify initialization/transport failure, valid runner `BLOCKED`, malformed runner output, `NEEDS_FIX`, and verification-command failure separately. A shell command that is still running, yielded a session ID, or has not delivered its final response and managed/adapter receipt is pending, not an initialization or transport failure: poll that same process/session until it exits and read its final result. Do not start a second runner while the first is pending. A valid `BLOCKED` receipt is a semantic result, not a transport failure; preserve the first valid receipt even if a later response differs. In managed mode, an SDK return with `processError`, timeout, or no `threadId` after `runTurn` was invoked does not prove that no provider work began; treat an incomplete return as `RUNNER_RESULT_BLOCKED` without a technical retry. A thrown error after invoking `runTurn` or the broker's invoke callback is likewise uncertain. For definitive initialization or transport failure before runner dispatch only, retry once with a new independent session and the same minimum payload. These technical starts do not create or consume an `attempt-NN`, change `initial` to `revalidation`, or authorize validation in the main context. If both starts fail, persist the canonical active `Delegation Blocker` singleton with `Kind: initialization` and stop in `RUNNER_INITIALIZATION_BLOCKED`. Malformed started output is not a transport retry; preserve its diagnostic. Persist the canonical malformed-output blocker only through the receipt-bound managed/adapter path. Only the same operation/slice may resume directly at delegation; a later valid attempt resolves the singleton atomically.

For every successfully started runner invocation with a valid result, append exactly one deterministic next `attempt-NN` with type, exact status, HEAD, verified scope, commands and exit codes, evidence, per-finding dispositions, new findings, blockers, unexpected workspace effects, and persistence summary. Preserve every earlier attempt. Formal validation is the only owner of finding state: every new finding created by `NEEDS_FIX` is born `active`; only a strictly later attempt may resolve it or supersede it with a same-kind finding whose origin is strictly later. A valid runner `BLOCKED` is persisted as that attempt and changes no finding state. A malformed response after start is not a transport retry. Persist an objective malformed-result blocker outside Validation Attempts only through the receipt-bound managed/adapter path; otherwise preserve the diagnostic and do not fabricate missing fields. The first formal `PASS` is terminal and no later attempt may be appended.

For managed `VALIDATE_SLICE` only, the adapter may request at most one format-only correction in the same runner thread after a provably completed final turn with malformed JSON syntax or a schema-invalid empty array in findingReferences/findingDispositions. The adapter validates the response with the existing local semantic schema before creating the deliverable file; unsupported schema failures block without another provider turn. The bounded local reference supports only one whole JSON Markdown fence, commas immediately before closing containers, one missing final object brace, and the explicit empty-set equivalence [] to the scalar "none" only in those two finding fields; nonempty arrays and all other value/type conversions are excluded. It must parse as a complete schema-valid validation payload before requesting repair. It must retain the original final message and both event turns, compare the complete reference token sequence (scalar bytes and punctuation in place, apart from the two explicitly recorded empty-set representations), reject changed content or structure, malformed second answer, tool use during repair, or changed thread, and retain a receipt diagnostic. A valid semantic `BLOCKED` or `NEEDS_FIX` is a verdict, not a format error. Pending, timed-out, failed, or uncertain turns never enter format repair. This correction cannot rerun validation or change requirements coverage and is not a transport retry or a new formal attempt; if the local equivalence check cannot prove unchanged content, stop with the malformed-result blocker. This bounded format/schema check does not establish whether the original evidence itself was accurate; formal validation retains that responsibility.

A failed marked verification command remains evidence even when a later corrected check passes. Neither the semantic command summary nor a later exit zero can erase that failure or authorize PASS in the same invocation. A demonstrated defect of the implementation remains NEEDS_FIX. Only a demonstrated defect of executor-prepared tests already required by current authority, on authorized paths in this slice and correctable within existing scope and rights, also requires NEEDS_FIX with a specific coverage finding. This includes a defective test, fixture or assertion or an objectively omitted required variant; it does not require a functional implementation bug. Identify the criterion/variant, violated contract, direct defect/omission evidence, authorized path and expected correction. Missing evidence alone does not establish a correctable test-delivery defect. The runner judges this semantically and remains read-only; only the executor corrects through APPLY_FINDINGS followed by VALIDATE_SLICE within existing budgets, with no extra call in this validation or REPLAN for a punctual omission. Invalid ad hoc checks outside this exception, access, transport, environment, insufficient authority and missing evidence without an identified correctable defect remain BLOCKED with the complete observed history. Use existing prepared checks and inspect their fixtures and assertions; the independent runner cannot create scripts or tests to fill missing coverage. Never PASS from an old suite or before sufficient evidence. A permitted destination does not authorize implicit shell temporary files. After a sandbox or permission denial, stop, retain the full diagnostic even after a final exit zero, and do not retry via another path, tool, temp setting or permission mode. A subsequent attempt requires the existing official handoff; this rule adds no retries or recovery budget.

Every finding must demonstrate a violated current requirement or required variant on an authorized path in this slice. A preference for a stronger assertion or an unrequired literal output string is not a coverage defect. This is semantic judgment, not a deterministic guarantee from the finding's wording. Formal `commands` must be nonempty and report actually executed verification commands and exits, even for NEEDS_FIX/BLOCKED; discovery and inspection never substitute for those commands. Do not fabricate evidence to satisfy the schema.

In managed mode, a `RUNNER_RESULT_BLOCKED` receipt may retain its exact rejected final bytes in `semanticResponseFile`, their hash, and null `semanticResponseStatus`. This is diagnostic evidence only. Pass the exact response file and receipt to the same `prepare-validation-candidate.mjs` boundary to prepare only the existing malformed-output Delegation Blocker, then strictly validate, publish and read back that blocker. The guard independently requires a concluded clean SDK turn, matching operation/slice/sequence/attempt/thread/authority, canonical paths, response hash and exact final event bytes. Uncertain completion or mechanical identity failures cannot publish it. No Validation Attempt, Effective Validation Base or PASS is created by a rejected receipt. Existing same-operation/slice recovery and budgets remain unchanged; never transcribe the receipt, repair semantic values or add a runner call here.

On `NEEDS_FIX`, validate and persist a complete deterministic disposition for every prior active finding: resolved findings receive a non-placeholder `Resolution` naming this attempt; superseded findings receive `Superseded by: finding-NN`; unresolved problems remain active. Append stable new findings for newly identified implementation problems or test-delivery defects within the narrow exception above, with severity, state `active`, origin attempt, problem, evidence, impact, related authority, and expected correction. Leave the Effective Validation Base unchanged or absent, keep the global row `[ ]`, leave final result pending, report explicit `APPLY_FINDINGS`, and stop. An authority/scope/strategy gap is instead formal `BLOCKED` with its concrete authority cause in the attempt, followed by its lifecycle handoff when needed and the already-legal `REPLAN` transition; it is never disguised as `NEEDS_FIX` and this skill does not create a divergence.

On `BLOCKED`, persist the concrete cause and missing prerequisite, leave the Effective Validation Base unchanged or absent, keep the global row `[ ]`, do not convert the status, and report a repeat `VALIDATE_SLICE` after its external prerequisite or explicit `REPLAN` when authority is the blocker. Stop.

On `PASS`, in this same operation:

1. validate the current attempt output and the complete final manifest before any mutation;
2. require all original changes, corrections, necessary effects, removals, relevant tests, and prior-slice overlaps, with justified regressions for affected earlier behavior;
3. reject incomplete, malformed, duplicate, unsorted, contradictory, or workspace-inconsistent manifest data and never invent hashes or results;
4. append the current `PASS` attempt without overwriting history;
5. atomically change every remaining applicable active blocking finding to `resolved` with a non-placeholder resolution naming this PASS attempt, or to `superseded` with a valid same-kind pointer; reject PASS if any active blocking finding would remain;
6. create or replace the entire Effective Validation Base so its origin is this current `PASS` attempt; for a fileless slice persist exact `Files: none`, objective `Fileless reason`, and `Changed Areas: none` without inventing a path or hash;
7. confirm the mandatory checklist, no active blocking finding or divergence, valid hashes, authoritative zero exit codes, and a consistent final result;
8. persist the final diff summary and `PASS` result and change exactly the selected global row from `[ ]` to `[x]` with validation/result `PASS`;
9. stop without selecting another slice.

For `VALIDATE_SLICE`, first use `runtime/prepare-validation-copy.mjs` to prepare the complete byte-identical official execution tree at the returned isolated `CANDIDATE_EXECUTION_ROOT`. Keep that candidate for diagnosis after rejection. Make only semantic finding-record/disposition and diff-summary edits, and keep `Validation Attempts`, `Effective Validation Base`, `Final Result`, and the selected `tasks.md` row byte-identical to live. Then execute exactly once `node "<SKILL_ROOT>/runtime/prepare-validation-candidate.mjs" --prepare --spec-path <SPEC_PATH> --slice <SLICE> --workspace <canonical workspace> --candidate-execution-root <CANDIDATE_EXECUTION_ROOT> --semantic-response-file <absolute-semanticResponseFile>`. In managed/adapter mode, the adapter persists the receipt before returning it; pass its absolute `receiptFile` literally to `--receipt-file`, alongside its `semanticResponseFile`. Do not transcribe the receipt JSON, copy it to another path, or reconstruct its filename. A missing `receiptFile` blocks persistence; reuse the captured files without another runner invocation while the official context and tested state remain unchanged. Omit `--receipt-file` in native mode. The helper under this installed skill root writes mechanical attempt/base/final/index fields into the isolated candidate before validation and hashes physical targets at preparation; it never edits live authority. After rejection, retain this candidate unchanged and use a fresh copy and fresh official preflight for any corrected proposal. Compose the complete candidate and execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --candidate <CANDIDATE_EXECUTION_ROOT>` before publishing them atomically. Candidate invocation and publication ownership are contract/model enforced; runtime parsing is strict but does not authorize the diff. When the candidate would become `COMPLETE`, the runtime also verifies final path ownership, SHA-256 values, `REMOVED`, reappearance, trusted-root containment, and symlink safety against the logical workspace before publication. Rejection preserves live bytes, so a runner `PASS` cannot bypass terminal integrity. After candidate PASS publish only this operation's selected task and global row, then use the final handoff command as strict readback. Never finalize from a historical attempt or accept a base whose origin is `NEEDS_FIX` or `BLOCKED`. A `[x]` `PASS` slice has exactly one valid Effective Validation Base; a `[x]` `SUPERSEDED` slice has no PASS requirement and is immutable; an open slice has `Final Result: pending`.

## Managed producer commands

When `STNL_MANAGED_CONTEXT` is present, this flow replaces the manual candidate/receipt/serializer/publication command sequences described above. After the official preflight, execute `node "$STNL_MANAGED_FINALIZER" --prepare` once; use only its returned candidate for authorized semantic edits. Prepare implementation and reusable checks on the approved slice paths before delegation. Write the one semantic JSON object into `$STNL_MANAGED_RUNNER_PAYLOAD` by file editing, then execute `node "$STNL_MANAGED_RUNNER_BRIDGE" --payload-file "$STNL_MANAGED_RUNNER_PAYLOAD"`. Do not feed stdin, pipes, heredocs or here-strings to the managed bridge. Execute `node "$STNL_MANAGED_FINALIZER" --finalize`; it binds the settled broker receipt, composes the existing producer/validator/publisher and reads official state. The main supplies no receipt ID, hash, manifest, verdict or mechanical path override.

A `PRIVATE_TESTS_FAIL` result preserves the failed record in the same isolated candidate. Only an authorized correction followed by the exact next automatic round can request another EXECUTE_SLICE/APPLY_FINDINGS runner, at most three rounds. Finalize each result before deciding what follows. The finalizer publishes only the existing terminal outcomes; a denial, uncertain start or rejected result does not authorize another round. VALIDATE_SLICE retains its one-result lock. A repeated finalization is idempotent only while the recorded candidate/live readback still agrees. On any disagreement preserve evidence and stop. Without managed context, retain the native/manual recipes and stdin adapter interface above.

## Allowed Effects

- obtain at most one valid-result invocation from the configured independent runner, with at most one additional initialization/transport start as specified above;
- update validation-owned sections in `tasks/slice-NN.md`;
- transition finding states only as part of one valid formal attempt;
- update exactly one `tasks.md` row only after valid `PASS` persistence.
- use temporary support files only outside the SPEC and execution root; never create scratch scripts, manifests, checklists, or ad hoc reports inside them.

## Blocks

Block invalid inputs, missing prerequisites, stale requirements authority, invalid attempt/finding history, any active blocking divergence, a non-canonical execution path or unsafe reserved SPEC entry reported by preflight, unavailable runner after the single technical retry, malformed runner output, incomplete Effective Validation Base data, incomplete finding dispositions, overlap without justified regressions, or persistence inconsistency. Arbitrary lifecycle-external or user-owned SPEC-root siblings are allowed and preserved. Never fall back to validation in the main context, delete an unknown path, or allocate an attempt for transport failure.

## Output

After persistence, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after VALIDATE_SLICE`. Report `PASS`, `NEEDS_FIX`, or `BLOCKED`, persisted evidence paths, whether the slice was completed, the runtime's normal handoff, every legal operation, and mandatory recovery as separate fields. A healthy `COMPLETE` readback has no normal execution handoff; `REPLAN` remains legal only for concrete later recovery. Terminal inspection is read-only and reports ownership drift with `REPLAN` recovery without reopening or revalidating a concluded slice. Stop.
