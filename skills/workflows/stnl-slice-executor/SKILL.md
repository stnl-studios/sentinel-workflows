# stnl-slice-executor

## Purpose

Run exactly one manual operation: `EXECUTE_SLICE` or `APPLY_FINDINGS`. Work on one explicit normalized slice, delegate every applicable test or verification command to the configured validation runner, persist only compact evidence, and stop before formal validation or global completion. A manual operation may contain a bounded automatic correction-and-recheck cycle; it never creates another manual operation.

## Inputs

- `SPEC_PATH`: required for manual launches. A directory must contain `feature_spec.md` and uses its `execution/` child; that file path resolves identically; another requirements file uses sibling `<stem>-execution/`. Block every other form. Managed launches use the cross-checked managed context and mechanical helper variables; never derive paths from a private home or thread name.
- `SLICE`: required and explicit. Accept one unsigned decimal number and normalize it to `slice-NN`; never infer it.
- Optional additional context may narrow the selected operation but cannot expand approved scope.
- For manual launches, use the configured independent runner. When `STNL_RUNNER_ADAPTER` is configured, invoke `node "$STNL_RUNNER_ADAPTER" --operation <OPERATION> --slice <slice-NN>` with the minimum payload on stdin and retain its absolute `semanticResponseFile` and receipt. Without an adapter or managed context, use a fresh independent native context with no inherited conversation history. Select the installed platform runner when supported (Codex `stnl_validation_runner`, Claude Code `@agent-stnl-validation-runner`). If the native API only spawns an independent generic agent, use `fork_turns:"none"` or its platform equivalent and require that agent, before any scope reads or checks, to read and follow the complete installed runner contract (Codex `~/.codex/agents/stnl_validation_runner.toml` `developer_instructions`; Claude Code `~/.claude/agents/stnl-validation-runner.md` body). Require the installed file to identify `stnl-validation-runner` and contain its canonical contract marker; a missing, malformed, or different runner contract blocks. Give it the official preflight identity and minimum operation payload, instruct it to follow the contract's no-write rule, and save its one raw JSON response in an absolute temporary file outside the SPEC. Identify this as a contract-loaded independent agent, not a selected registered runner type. Reading `developer_instructions` from a file is task-level instruction loading; it does not confer developer-level priority or the enforcement guarantee of a registered agent. If independent spawning or exact contract loading is unavailable, block; a generic agent without that contract is not the runner. Managed launches use the pathless bridge below. The human launcher supplies no helper path or benchmark sequence.

## Authority

Current requirements authority and approved plans define scope. `tasks.md` defines global progress and is read-only for this skill. The selected detailed task file authorizes local work and records execution. Its `Requirements authority` and `Plan revision` must match the current open slice and deterministic preflight. The configured independent runner owns only the check result; it does not own implementation, correction, persistence, the formal validation verdict, or completion. Other slice artifacts are out of scope unless a concrete dependency must be checked read-only.

Execution preflight is read-only. An accepted mandatory resume includes a structured `MANDATORY_RECOVERY` record; an incompatible request includes structured `RECOVERY_TARGETS`. Preserve those fields exactly. Only when preflight reports a mechanical violation for the exact `Findings IDs` alias or the exact historical `Check discovery sources` / `Check discovery actions` pair may this skill explicitly run `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --repair-known-contract` once and repeat the original preflight; every other contract violation blocks.

## Minimum Reads

- `plan.md`, `tasks.md`, selected detailed plan and task file;
- requirements referenced by the selected slice;
- local `references/execution-record-schema.md` before persisting or interpreting findings, divergences, checks, or supersession;
- directly related code, tests, imports, dependencies, and prior compact test evidence only.

## Delegated Checks
The delegated runner returns only one raw JSON semantic object for `EXECUTE_SLICE` or `APPLY_FINDINGS`, using the exact lowerCamelCase machine keys for that operation. In managed/adapter mode, `commands` are non-authoritative claims: marked SDK command events supply exact command text and observed exit. In native mode, the independent runner must actually execute applicable checks and report their literal commands and observed numeric exits in `commands`; the serializer records those runner-reported values without claiming mechanical capture. Every verification command uses the literal `STNL_VERIFICATION_COMMAND=1 ` shell prefix; discovery commands are unmarked. The runner does not emit `Operation`, `Type`, `Tested scope`, `Tested state`, task-relative paths, mechanical labels, hashes, records, or formal manifests; the deterministic producer owns those fields and maps the machine keys to the canonical labels. If a semantic value cannot be represented by the strict JSON shape, require the complete JSON object with `status: "BLOCKED"`.

Before content reads, implementation, correction, or delegation, manual launches execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> <OPERATION> <SLICE>`. Managed launches execute pathless `node "$STNL_MANAGED_PREFLIGHT"`, which reads the cross-checked context and validates operation/slice, authority, state, and legal recovery. The structural, state, serial-order, requirements-authority, task-schema, active-record, recovery-target, and third-failure gates are deterministic authority. Read the current requirements authority only from the exact `authority=sha256:<64hex>` field returned by that same official preflight, require it to equal the selected artifacts, and copy it byte-identically only into candidate records that carry the authority; the adapter supplies it mechanically to the runner. Never hash `shared/requirements.md`, `feature_spec.md`, or any other raw file, and never reconstruct the canonical authority. When preflight and selected artifacts agree, a different producer-supplied value is not documentary divergence. When preflight blocks, preserve its exact state-derived diagnostic, including the concrete legal operation and slice when present; never substitute values inferred from the current request. Missing or invalid input, an absent slice or artifact, an incomplete serial dependency, an unapproved or stale plan, absent tasks, a concluded slice, an active blocking divergence, an out-of-phase operation, or prior `3/3 TESTS_FAIL` blocks before implementation or correction and therefore before any runner invocation. Once implementation or correction has occurred, the operation cannot end without invoking the configured independent runner.

After implementation or correction, determine the final changed and removed scope and write it to the isolated execution candidate before delegating the runner, without running verification commands in the main context. `Changed Areas` MUST NOT remain the pristine `- pending` sentinel after any file-backed implementation or correction; replace it with every final affected or removed path, or use exact `- none` only for a genuinely fileless operation with an objective fileless reason. Keep the live task unchanged until the complete candidate passes validation and publication. Tests, builds used as verification, linters, typechecks, compilations, validators, contract checks, migration checks, and regression suites are runner-only work.

Prepare reusable tests in the authorized implementation or correction before delegation, covering every applicable acceptance criterion and its required variants. Include those tests in the final Changed Areas. Writing tests is implementation work; executing verification remains runner-only. Give the runner concrete existing test paths and coverage intent, not an instruction to create an ad hoc script. Build fixtures from the existing input and persistence contracts; preserve the required assertions and variants, and do not expand those contracts to make a fixture valid. An old passing suite that omits the new behavior is insufficient. Do not depend on heredocs, here-strings or nested shell quoting to generate multiline programs: the shell may need an implicit temporary file outside the permitted destination. If a command reports a sandbox or permission denial, stop and preserve the full diagnostic even when its final exit is zero; do not retry via another path, tool, temp setting or permission mode.

Start each logical runner invocation in a new independent delegated session with no inherited conversation history. In managed mode use only pathless `node "$STNL_MANAGED_RUNNER_BRIDGE" --payload-file "$STNL_MANAGED_RUNNER_PAYLOAD"`; native delegation cannot replace its broker or receipt. In native mode, use the installed named runner or the contract-loaded independent agent described in Inputs; that agent itself performs discovery and verification under the complete installed runner contract, while the main context performs none. Send one JSON object with `automaticCheckRound` (`1/3`, `2/3`, or `3/3`) and `changedAreas` (an array of canonical task-relative claims matching the task's Changed Areas; `[]` for a legitimate fileless task) for EXECUTE_SLICE and APPLY_FINDINGS. A fileless payload also requires a nonempty `filelessReason`; a file-backed payload must omit it. Optional semantic fields are `activeFindings` and `corrections` string arrays, plus nonempty `relevantEvidence` and `requestedChecks` strings. Do not use aliases such as `automaticRound` or `changedScope`. VALIDATE_SLICE does not need `changedAreas`. In managed/adapter mode, do not repeat adapter, snapshot, bridge, preflight, operation, `SPEC_PATH`, workspace, execution root, slice, plan/task paths, or requirements authority in that semantic payload; the adapter supplies the canonical mechanical envelope. In native mode, include the official preflight's operation, slice, authority and concrete canonical SPEC/workspace/plan/task paths in the runner handoff so it can inspect the right scope. Resolve those paths from the manual launcher and official preflight, not private-home identity. Never send conversation history or full logs, and never substitute a source checkout, CWD-relative, candidate, placeholder, or reconstructed path. A missing or mismatched mechanical path is a handoff defect before the runner, not a valid runner `BLOCKED` result. Before accepting any runner status, require each file-backed `Tested state` entry to be task-relative from `dirname(tasks/slice-NN.md)` to its physical target; `src/...`, `test/...`, absolute, CWD-relative, or repository-relative paths are malformed and must never be rebased or accepted. The runner remains read-only over code and execution artifacts.
After deriving each task-relative claim, require the producer to resolve `path.resolve(dirname(taskArtifact), claim)` and compare it by `realpath` with the physical target that will be hashed; claims derived from `SPEC_PATH`, SPEC root, plan, CWD, or workspace root, or claims that omit a task-artifact parent, are malformed and cannot produce `TESTS_PASS`. Do not repair or reinterpret the claim in the runtime.

Invoke the configured independent runner at least once and at most three times within the same manual operation. The first invocation is mandatory after the initial implementation or correction and cannot be skipped because the change appears simple or because no check is expected to apply; the runner performs independent discovery and returns `TESTS_NOT_APPLICABLE` when appropriate. The local invocation budget starts at three for each `EXECUTE_SLICE` or `APPLY_FINDINGS` invocation and is never shared with a later operation. Each successfully started runner request carries the applicable minimum payload and the automatic round as `1/3`, `2/3`, or `3/3`. It returns only the schema for that operation with exactly `TESTS_PASS`, `TESTS_FAIL`, `TESTS_NOT_APPLICABLE`, or `BLOCKED`.

Persist every valid result append-only in the isolated candidate via the serializer before deciding what follows. After `TESTS_FAIL` in round one or two, this private append is the required persistence before correction; do not run the publication validator or publisher yet. Implementation checks use the next global `implementation-check-NN`; findings checks use the next global `findings-check-NN`. A later manual invocation has its own three-call budget but continues each section's sequence instead of resetting it. Every record includes the automatic round and limit, tested state, verification commands with numeric exit codes, failures, corrections covered, scope, discovery sources and relevant read-only discovery actions, non-applicability rationale, unexpected workspace effects, and compact persistence summary. `TESTS_NOT_APPLICABLE` is valid only after objective discovery and when no verification command was executed; read-only actions used only to discover applicable checks are permitted and recorded under canonical `Discovery sources`.

Classify delegation outcomes before persistence: initialization/transport failure, valid runner `BLOCKED`, malformed runner output, and valid `TESTS_FAIL` are distinct. An executed verification command failing because of an objective defect in an executor-prepared test, fixture or assertion is `TESTS_FAIL` when the evidence identifies a correction inside the approved slice and existing rights; it need not demonstrate an implementation defect. Preserve the command, exit, violated contract and diagnostic, and do not claim unverified behavior passed. Only the main context may correct after persistence, under the existing round-one/two correction gate and three-call budget. Sandbox or permission denial, a genuinely unavailable tool, dependency or input, or an objective lack of sufficient runnable checks remains `BLOCKED`; never convert these causes to fixture defects or bypass the denial. A valid `BLOCKED` is a runner result, not a transport failure. Formal `VALIDATE_SLICE` retains its separate `PASS`/`NEEDS_FIX`/`BLOCKED` judgment and evidence requirements.

For an initialization or transport failure only, retry the same logical invocation at most once using a new independent session and the same minimum payload. A shell command that is still running, yielded a session ID, or has not yet delivered its final response (and, in managed/adapter mode, receipt) is pending, not an initialization or transport failure: poll that same process/session until it exits and read its final result before considering any retry. Do not inspect unrelated processes or start a second runner while the first process is pending. Neither technical start attempt consumes automatic round `1/3`, `2/3`, or `3/3`, creates a `Validation Attempt`, allocates `implementation-check-NN` or `findings-check-NN`, or authorizes a code correction. If the second start also fails, persist exactly one active `Delegation Blocker` singleton with `Kind: initialization` under the selected task's canonical section, both compact transport causes, and the required action, then stop in `RUNNER_INITIALIZATION_BLOCKED`. A malformed response after the runner started is not retried as transport; preserve its diagnostic without allocating a check identifier. Only use receipt-bound malformed-output persistence when that receipt exists.

When the same stored operation and slice are invoked again from either runner-blocked state, resume directly at the logical runner invocation. This exact persisted delegation recovery remains legal when later formal-validation history exists; it does not reopen implementation or authorize finding correction. Do not reimplement, reapply findings, duplicate checklist or diff summaries, duplicate the blocker, reset global identifiers, or allocate an automatic round or check identifier before a runner session actually starts. If transport fails definitively again, update the existing singleton instead of appending another record. A later valid record resolves it atomically under `references/execution-record-schema.md`.

The operation may end after implementation or correction only after a valid auxiliary status is received or a definitive delegation blocker is persisted. If native malformed output cannot be persisted without a bound receipt, stop with the preserved diagnostic and no publication; never claim a live recovery state that was not written. Before a terminal implementation result (`TESTS_PASS`, `TESTS_NOT_APPLICABLE`, or round `3/3 TESTS_FAIL`) is added to the isolated candidate, every mandatory checklist item and its related execution state must already be complete in that same candidate. Candidate validation rejects the inverse ordering. `TESTS_PASS`/`TESTS_NOT_APPLICABLE` then enter `IMPLEMENTED_AWAITING_VALIDATION`; valid runner `BLOCKED` enters `AUXILIARY_BLOCKED`; and round `3/3 TESTS_FAIL` enters `IMPLEMENTATION_RETRY_EXHAUSTED`. Findings outcomes retain their existing `FINDINGS_CORRECTED`, `AUXILIARY_BLOCKED`, and `FINDINGS_RETRY_EXHAUSTED` transitions. Additional automatic rounds occur only after `TESTS_FAIL` in round one or two and an authorized correction. Normally, retry exhaustion permits only explicit `VALIDATE_SLICE` and neither executor operation may re-enter until that formal verdict establishes the next state. Never make a fourth automatic invocation, use an unbounded loop, fall back to checks in the main context, invent a result, implement or correct through the runner, create a Validation Attempt or Effective Validation Base, set a final result, mark `[x]`, or continue automatically to another operation, including `VALIDATE_SLICE`.

One narrow live-state recovery overrides that normal handoff. If the shared runtime finds a terminal implementation result with an incomplete mandatory checklist, it preserves the observed lifecycle state but makes only `EXECUTE_SLICE` for that same slice mandatory, owned by `stnl-slice-executor`, with the concrete implementation record and round. Wrong-slice, validation, replan, and unrelated requests must preserve that target and block. Re-enter only to make the approved implementation/checklist record truthful and complete; preserve the terminal auxiliary record and any formal-validation history, do not allocate another check after a terminal record, and do not modify findings or validation records. Repeated invocation before publication is the same recovery. After candidate validation and one complete selected-task publication, normal validation or retry-exhaustion authority resumes automatically. This is not a generic `IMPLEMENTED_AWAITING_VALIDATION` bypass.

After `TESTS_FAIL` in round one or two, the main context may correct only when the failure evidence objectively identifies a correction inside the approved slice, without changing requirements or strategy, replanning, modifying another slice, or treating an unrelated preexisting failure. Before the next runner invocation, update canonical file-backed `Corrections Applied` path claims; a genuinely fileless correction keeps exact `- none` and uses exact `Correction paths: none` with objective `Fileless reason`, correction rationale, and verification evidence. Persist the reported failure, evidence, applied change, affected files or fileless absence, updated scope, and in-slice rationale in the next auxiliary check's prior-round correction fields. Preserve every earlier check and correction claim.

For `EXECUTE_SLICE`, `Corrections Applied` is cumulative history, while each round's producer-owned `Correction paths` is the code delta against the preceding failed round's `Tested state`. An authorized correction to verification conditions without a code change keeps cumulative claims and file-backed Tested state; record its objective cause and correction in the existing explanatory fields. The producer emits exact `Correction paths: none` for that unchanged delta, and strict validation requires identical tested paths and digests to the preceding round. Do not invent a path or `Fileless reason` for this case, clear historical claims, change any verdict, expand permissions, or add a fourth invocation.

## EXECUTE_SLICE

### Assessment of an objective blocker before checklist completion

After a successful official `EXECUTE_SLICE` preflight, if approved implementation has already changed file-backed paths but an objective missing input, unavailable verification condition, or conflict between the approved verification strategy and existing requirements prevents completing a mandatory checklist item, delegate a bounded independent assessment before completing that item. This exception overrides only the checklist-before-delegation and reusable-check preparation ordering for the blocked criterion; preserve every incomplete item as pending. Identify the exact criterion, objective evidence, required action, and existing reusable checks in `relevantEvidence` / `requestedChecks`. Prepare the candidate's exact approved Changed Areas before dispatch, including all affected implementation and test paths. Do not implement a new requirement or change strategy to make the checklist complete.

The runner independently determines the result under its existing contract; do not request a preferred verdict or reinterpret a partial passing suite as complete coverage. With an incomplete checklist, only a valid `BLOCKED` assessment may be published through the existing serializer, strict candidate validator, and selected-task publisher. Preserve the raw response and diagnostic for any rejected result; never convert `TESTS_PASS` to `BLOCKED`, manufacture hashes, or allocate another round after a rejected terminal result. Record any independently confirmed strategy/authority conflict as an active blocking divergence in that same candidate, with the canonical required authority operation, so the official readback routes to `RESUME` or `REPLAN`. A blocker without such a divergence retains the existing `AUXILIARY_BLOCKED` recovery.

This assessment uses the existing independent runner, full response schema, current Tested state capture, and operation-local three-call budget. It grants no extra invocation, does not bypass a failed preflight, an already active divergence, persisted same-operation recovery, terminal-checklist recovery, or retry exhaustion, and does not reopen a superseded slice or rewrite historical evidence. `TESTS_PASS`, `TESTS_NOT_APPLICABLE`, and round `3/3 TESTS_FAIL` still require every mandatory checklist item complete before their terminal record is added.

Require an open, dependency-ready current-authority slice with approved plans and materialized tasks. Implement only its checklist. Update local checklist items, canonical normalized `Changed Areas` path claims, discovered expansion, divergences, and a compact diff summary in the isolated candidate. For every file-backed execution-record field defined as task-relative, derive the stored path from the selected final live task artifact itself: `path.relative(dirname(tasks/slice-NN.md), physicalTarget)`, normalized to `/`. The prepared candidate task has exactly the same depth as that live task, so the claim resolves to the same physical target from either path. This applies to executor-owned `Changed Areas` and `Corrections Applied` and to the runtime-owned `Tested state` and correction paths. Never derive those values from the process CWD, workspace root, repository root, or SPEC root; never repair or reinterpret an incorrectly based producer value. Persist every divergence under local `references/execution-record-schema.md`; newly detected blocking divergences are `Severity: blocking`, `State: active`, and direct first to lifecycle `RESUME` when documentary authority must change, then to `REPLAN`. The executor never resolves or supersedes a divergence. Except for the objective-blocker assessment above, verify every mandatory checklist item complete in the candidate before delegating checks, then append the result under `Implementation Test Evidence` as the next `implementation-check-NN`, including status, tested state, commands and numeric exit codes, selected tests, selection rationale, coverage, compact evidence or failure summary, blockers, unexpected workspace effects, and persistence summary. The narrow existing-inconsistency recovery above instead preserves its existing terminal implementation record.

For every file-backed `Tested state`, the managed/adapter runtime captures the physical target hash when the runner finishes; the native producer hashes the physical target at serialization. The deterministic producer inserts the resulting digest as complete lowercase 64-hex SHA-256 into the isolated candidate. Never hand-type, truncate, abbreviate, or substitute a digest; do not manually copy it from command output. If candidate validation rejects a generated record, distinguish producer failure from a candidate transcription or layout error; preserve the rejected candidate and regenerate a fresh candidate from unchanged live authority and the same valid semantic response when the code and tested state are unchanged.
For managed launches, use exactly the snapshot-owned serializer in `$STNL_RUNNER_EVIDENCE_SERIALIZER`; if it is absent, block. For a manual native launch without managed context or `STNL_RUNNER_ADAPTER`, use the existing official `runtime/serialize-runner-evidence.mjs` under this installed skill root (`<SKILL_ROOT>`). No environment variable or receipt is required on that native path. Do not search a private home, source checkout, or benchmark snapshot for another serializer. The serializer runs before publishing any candidate that requires evidence persistence; never pass its path to the runner.

For `EXECUTE_SLICE` and `APPLY_FINDINGS`, native launches save the runner's one raw JSON object unchanged to a temporary file outside the SPEC. The native invocation is `node "<SKILL_ROOT>/runtime/serialize-runner-evidence.mjs" --execution-bundle --operation <requested-operation> --workspace <canonical workspace> --task-artifact <candidateTaskArtifact> --semantic-response-file <absolute-temp-file> --insert-candidate`, with no `--receipt-file`. In managed/adapter mode use the configured serializer and add `--receipt-file <receiptFile>`; its bound events and captured Tested state remain authoritative. The adapter persists the receipt before returning it; pass its absolute `receiptFile` literally to `--receipt-file`, alongside its `semanticResponseFile`. Do not transcribe the receipt JSON, copy it to another path, or reconstruct its filename. A missing `receiptFile` blocks persistence; reuse the captured files without another runner invocation while the official context and tested state remain unchanged. The candidate task is the same-depth sibling returned by `prepare-execution-copy.mjs`, with completed `Changed Areas` and applicable `Corrections Applied`; never use `--spec-path` for this bundle because that selects the still-pristine live task. The producer canonicalizes those sections against approved Checklist targets, derives physical targets, and inserts the complete canonical `implementation-check-NN` or `findings-check-NN` record. In native mode it hashes the physical targets at serialization and records the independent runner's reported commands and exits as runner-reported evidence. In managed mode it uses receipt-bound Tested state captured at runner completion and marked command events. In both modes it writes task-relative paths, exact delimiters and complete SHA-256 digests; the main context does not transcribe them. A producer rejection with a matching managed receipt can persist the deterministic malformed-output Delegation Blocker. A missing fileless reason or a file-backed response carrying that reason is a semantic response/scope defect; never supply or infer the reason on the runner's behalf. Before the first valid auxiliary record, receipt-bound recovery restores the unchanged live scope and checklist in the candidate, leaving them pending under the canonical blocker until valid evidence arrives. Preserve private checks already persisted in the bounded cycle; a candidate that remains inconsistent still blocks publication. This does not widen the single format-repair allowance or authorize another automatic recovery after its existing budget is used. Without that receipt, preserve the rejected candidate and diagnostic and block publication; do not manufacture a receipt or claim mechanical capture. Under unchanged official authority, a correctable candidate defect may be rebuilt from live and the same valid semantic response only while code and tested state remain unchanged. Never repair a rejected candidate after validation. Neither operation invokes legacy `--record` or `--response` from the runner.

In native mode, write the independent runner's raw final JSON response unchanged to the absolute temporary semantic response file; retain the runner's actual command results in its `commands` field. In managed/adapter mode the adapter owns raw-response capture. When its receipt contains an absolute `semanticResponseFile`, use that file as the sole source of the final runner response, pass it byte-for-byte to the deterministic evidence producer, and do not inspect the tail of `eventsPath` to infer whether a final response exists or invoke a second capture. `RUNNER_RESPONSE_CAPTURED` denotes semantic acceptance; `RUNNER_RESULT_BLOCKED` with a response file denotes rejected diagnostic bytes with null `semanticResponseStatus` and their hash, never a verdict. Pass that exact file and receipt to the same producer only to prepare the existing malformed-output Delegation Blocker. Its managed identity/conclusion guard must pass before candidate validation and publication; no check or attempt is allocated. A receipt with no response file, uncertain completion, mismatched identity/authority/path/hash or SDK final bytes blocks publication. Existing same-operation/slice recovery and budgets remain unchanged. If the receipt has no `semanticResponseFile`, follow its failure status; never infer response absence from a JSONL tail. If the adapter returns only structured JSONL output, capture it with the exact absolute `capture-runner-response.mjs` helper path resolved from this skill root, using `--structured-output-file <absolute-runner-output> --output <absolute-temp-file>`. The capture helper extracts the final `agent_message` and writes its JSON object byte-for-byte; it rejects invalid JSON, arrays, JSON string literals, and absent messages. The existing serializer remains the strict producer and candidate validation remains authoritative.
Before accepting `TESTS_PASS`, require the producer to insert each file-backed digest as exactly `sha256:` plus 64 lowercase hexadecimal characters and require strict candidate validation. A managed captured semantic response rejected deterministically by the producer is persisted as `RUNNER_RESULT_BLOCKED` through the matching receipt and canonical Delegation Blocker. A native producer rejection or insertion/environment failure without that receipt remains a separate diagnostic and blocks publication.
Every file-backed `Tested state` tuple must use the literal `sha256:` delimiter; `sha256=` or any other separator is malformed output; use receipt-bound `RUNNER_RESULT_BLOCKED` persistence only when available, otherwise block publication with the diagnostic.
The deterministic producer's serialized tuple forms are exact: each file-backed `Tested state` line is `- \`<task-relative path>\` | sha256:<64 lowercase hex>` or `- \`<task-relative path>\` | REMOVED`, and each semantic runner `Commands` line is `- \`<full command>\` | exit:<integer>`. Pipe, backticks, the literal `sha256:`/`REMOVED`, and `exit:` marker are mandatory in the respective producer output; the runner does not manufacture the file-backed tuple.
When classifying runner output, if the official preflight, payload, and selected artifact carry the same canonical authority token, discard any raw requirements-file SHA mentioned by the response; never copy, compare, report it as a divergence, or block because of it. Only a missing or unequal official token may block authority. A genuinely malformed runner schema blocks on that defect; report `RUNNER_RESULT_BLOCKED` only after its receipt-bound blocker was actually published.

Compare every changed path with the Effective Validation Bases of earlier completed slices. Record each overlap under `Prior Validation Overlap` with the earlier slice, affected behavior, and regressions the current validation must justify. The model may use the compact semantic carrier `- Slice NN overlap: <path claims>; <behavior and regression rationale>`; the validation producer extracts only those physical path claims and serializes the canonical evidence deterministically. Include the path in the current slice's changed areas. Do not reopen or rewrite an earlier slice.

On `TESTS_FAIL` before the third round, apply only an objectively supported in-scope correction, update changed scope, record the correction, and invoke the runner again within the same `EXECUTE_SLICE`. If that correction is not authorized, append the applicable active blocking divergence and stop. On the third `TESTS_FAIL`, persist evidence, enter `IMPLEMENTATION_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist discovery sources, relevant read-only discovery actions, verification types considered, objective rationale, and confirmation that no verification command was executed. On `BLOCKED`, record the cause and required action and enter `AUXILIARY_BLOCKED`. Every status leaves the slice open and formal validation pending; no check creates a formal finding or invokes another operation automatically.

## APPLY_FINDINGS

Require at least one persisted active blocking finding in `VALIDATION_NEEDS_FIX`, and reject retry-exhausted or already-corrected phases. Read active findings, the selected plan and task record, affected code and tests, and necessary requirements. Correct only reported problems and their necessary effects. For file-backed work, add every final affected or removed path to canonical `Changed Areas` and `Corrections Applied`, deriving each stored value with `path.relative(dirname(tasks/slice-NN.md), physicalTarget)` from the selected final task artifact and normalizing separators to `/`. Persist runtime-owned `Tested state` and mechanically derived correction paths on that same basis; never request `correctionPaths` from the runner. For a genuinely fileless correction, keep both sections exact `- none`, never invent a path/hash, and persist objective reason, correction rationale, and verification evidence in the existing check fields. Preserve all finding records, Validation Attempts, and any historical Effective Validation Base until later formal validation; correction and auxiliary checks never change finding state.

In managed mode, the broker seals the current authorizing `NEEDS_FIX` cycle, active finding IDs, slice, sequence, fingerprint, round and candidate hashes from official state before dispatch. Principal `activeFindings` descriptions are context only. The runner need not return `findingsCycle`; any legacy value is retained raw as diagnostic and never interpreted as authority. The producer uses sealed ownership, preserves runner verified/unsupported judgments and validates prospective evidence before private append. Native production derives the cycle from current formal state as well.

Then delegate checks automatically and append the result under `Findings Test Evidence` as the next `findings-check-NN`, associated with the applicable findings cycle. `Finding IDs` is the canonical target set; `Findings verified` is a canonical subset (or `none`); `Unsupported active findings` is every active finding in that cycle not verified by the check. In addition to those sets, record corrections covered and regressions selected.

On `TESTS_FAIL` before the third round, adjust only persisted active findings, failures introduced or exposed by their corrections, directly related regressions, and necessary effects inside approved scope. Update corrections and changed scope, record the between-round correction, and invoke the runner again within the same `APPLY_FINDINGS`. On the third `TESTS_FAIL`, persist evidence, leave every previously active finding active while preserving historical states, enter `FINDINGS_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist objective discovery, relevant read-only discovery actions, verification types considered, rationale, and confirmation that no verification command was executed without resolving findings. On `BLOCKED`, preserve cause and required action and enter `AUXILIARY_BLOCKED`. Do not perform formal validation, mark completion, set final result, replace prior Validation Attempts or Effective Validation Base, or invoke `VALIDATE_SLICE` automatically. If correction requires a requirement, scope, dependency, or strategy change, append an active blocking divergence and direct first to lifecycle `RESUME` when needed and then explicit `REPLAN`.

## Execution artifact publication

Never append or replace a live execution record directly. Run `node "<SKILL_ROOT>/runtime/prepare-execution-copy.mjs" --prepare --spec-path <SPEC_PATH> --slice <SLICE>` to copy the complete execution tree to its owned same-depth sibling outside the SPEC and inside the canonical workspace. Apply only executor-owned changes to `candidateTaskArtifact` and pass that exact artifact to the execution evidence producer. For both `EXECUTE_SLICE` and `APPLY_FINDINGS`, keep intermediate `TESTS_FAIL` records private while applying the authorized correction and obtaining the next runner result within the existing three-call budget. Only when the bounded cycle ends in `TESTS_PASS`, `TESTS_NOT_APPLICABLE`, round `3/3 TESTS_FAIL`, or a canonical blocking outcome, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --candidate <CANDIDATE_EXECUTION_ROOT>`. This invocation and publication ownership are contract/model enforced; the runtime enforces strict candidate parsing when called, rejects terminal implementation evidence paired with an incomplete checklist, but is not a publisher and does not authorize the diff. A rejected candidate consumes no additional runner call, check round, identifier, or live history. Preserve the rejected candidate and exact diagnostic. If the cause is correctable under unchanged official authority, create a new candidate from live, apply the diagnosed correction, validate it strictly, and publish only that valid new proposal. Never mutate or republish a rejected candidate. After candidate PASS, run `node "<SKILL_ROOT>/runtime/prepare-execution-copy.mjs" --publish --spec-path <SPEC_PATH> --slice <SLICE> --candidate-root <candidateRoot>`; the helper rechecks unchanged live authority and candidate validity, atomically replaces only the selected task, and removes only its owned successful candidate. Never expose the checklist and terminal implementation record as separate live writes. Then execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after <OPERATION>` as the strict readback before declaring the record persisted. Treat this readback as read-only: require exit zero and inspect the resulting state, normal handoff, legal operations, required recovery handoff, and mandatory same-operation recovery; block on a nonzero exit, malformed output, or reported contract diagnostic. Do not repeat the original operation preflight: it authorized work in the initial state and may correctly reject that operation after publication.

## Managed producer commands

When `STNL_MANAGED_CONTEXT` is present, this flow replaces the manual candidate/receipt/serializer/publication command sequences described above. After the official preflight, execute `node "$STNL_MANAGED_FINALIZER" --prepare` once; use only its returned candidate for authorized semantic edits. Prepare implementation and reusable checks on the approved slice paths before delegation. Write the one semantic JSON object into `$STNL_MANAGED_RUNNER_PAYLOAD` by file editing, then execute `node "$STNL_MANAGED_RUNNER_BRIDGE" --payload-file "$STNL_MANAGED_RUNNER_PAYLOAD"`. Do not feed stdin, pipes, heredocs or here-strings to the managed bridge. Execute `node "$STNL_MANAGED_FINALIZER" --finalize`; it binds the settled broker receipt, composes the existing producer/validator/publisher and reads official state. The main supplies no receipt ID, hash, manifest, verdict or mechanical path override.

A `PRIVATE_TESTS_FAIL` result preserves the failed record in the same isolated candidate. Only an authorized correction followed by the exact next automatic round can request another EXECUTE_SLICE/APPLY_FINDINGS runner, at most three rounds. Finalize each result before deciding what follows. The finalizer publishes only the existing terminal outcomes; a denial, uncertain start or rejected result does not authorize another round. VALIDATE_SLICE retains its one-result lock. A repeated finalization is idempotent only while the recorded candidate/live readback still agrees. On any disagreement preserve evidence and stop. Without managed context, retain the native/manual recipes and stdin adapter interface above.

## Allowed Effects

In managed mode the finalizer prepares and strictly validates an owned working copy before publishing. Its persisted preparation is bound to the canonical receipt, sealed request, candidate owner, authority and complete input/live/evidence hashes. Repeating `--finalize` after an I/O failure reuses the validated preparation without appending another check or attempt. After publication it may seal only the finalization record when the complete live image and evidence still agree; it never republishes over a foreign change. Semantic rejection retains both the input and rejected working copy. Only after a recorded rejection or interrupted preparation, use `--prepare` with fresh official preflight to obtain a new candidate for authorized semantic edits; preserve the old copies and reuse the settled receipt while its tested state and authority remain valid. This recovery allocates no runner invocation or automatic round. A failure before candidate binding retains the allocated copy; a matching immutable owner can finish that binding, while an unbound copy without an owner remains diagnostic evidence.

- modify implementation and tests inside the selected scope;
- after implementation or correction, invoke the configured independent runner at least once and no more than three times in the selected manual operation;
- update only execution-owned sections of `tasks/slice-NN.md`, including the appropriate append-only test-evidence section.
- use temporary support files only in an external operating-system temporary directory; never create scratch files, scripts, manifests, or ad hoc reports inside the SPEC or execution root.

## Blocks

Block missing or invalid inputs, absent artifacts, incomplete dependencies, stale requirements authority, a concluded slice, an active blocking divergence, either normally consistent retry-exhausted state, out-of-scope work, a required planning/requirements decision, a non-canonical execution path or unsafe reserved SPEC entry reported by preflight, unavailable or malformed runner behavior after the bounded transport policy and objective persistence above, or an attempt to mutate plans, the global task index, another slice, or a concluded slice. The exact checklist-inconsistency and persisted same-operation delegation recoveries above are the only exceptions to the normal phase/history gates. Arbitrary lifecycle-external or user-owned SPEC-root siblings are allowed and preserved. Report each blocking path exactly and require relocation or explicit removal; never delete it automatically.

## Output
