# stnl-slice-executor

## Purpose

Run exactly one manual operation: `EXECUTE_SLICE` or `APPLY_FINDINGS`. Work on one explicit normalized slice, delegate every applicable test or verification command to the configured validation runner, persist only compact evidence, and stop before formal validation or global completion. A manual operation may contain a bounded automatic correction-and-recheck cycle; it never creates another manual operation.

## Inputs

- `SPEC_PATH`: required for manual launches. A directory must contain `feature_spec.md` and uses its `execution/` child; that file path resolves identically; another requirements file uses sibling `<stem>-execution/`. Block every other form. Managed launches use the cross-checked managed context and mechanical helper variables; never derive paths from a private home or thread name.
- `SLICE`: required and explicit. Accept one unsigned decimal number and normalize it to `slice-NN`; never infer it.
- Optional additional context may narrow the selected operation but cannot expand approved scope.
- For manual launches, resolve the independent runner from the active platform adapter. When `STNL_RUNNER_ADAPTER` is configured, invoke `node "$STNL_RUNNER_ADAPTER" --operation <OPERATION> --slice <slice-NN>` with the minimum payload on stdin; the adapter returns an absolute `semanticResponseFile` receipt. Otherwise use the configured independent runner with the same payload and capture contract. Managed launches use the pathless bridge below. The human launcher supplies no helper path or benchmark sequence.

## Authority

Current requirements authority and approved plans define scope. `tasks.md` defines global progress and is read-only for this skill. The selected detailed task file authorizes local work and records execution. Its `Requirements authority` and `Plan revision` must match the current open slice and deterministic preflight. The configured independent runner owns only the check result; it does not own implementation, correction, persistence, the formal validation verdict, or completion. Other slice artifacts are out of scope unless a concrete dependency must be checked read-only.

Execution preflight is read-only. An accepted mandatory resume includes a structured `MANDATORY_RECOVERY` record; an incompatible request includes structured `RECOVERY_TARGETS`. Preserve those fields exactly. Only when preflight reports a mechanical violation for the exact `Findings IDs` alias or the exact historical `Check discovery sources` / `Check discovery actions` pair may this skill explicitly run `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --repair-known-contract` once and repeat the original preflight; every other contract violation blocks.

## Minimum Reads

- `plan.md`, `tasks.md`, selected detailed plan and task file;
- requirements referenced by the selected slice;
- local `references/execution-record-schema.md` before persisting or interpreting findings, divergences, checks, or supersession;
- directly related code, tests, imports, dependencies, and prior compact test evidence only.

## Delegated Checks
The delegated runner returns only one raw JSON semantic object for `EXECUTE_SLICE` or `APPLY_FINDINGS`, using the exact lowerCamelCase machine keys for that operation and `commands` as objects containing only `command` and integer `exit`. The runner does not emit `Operation`, `Type`, `Tested scope`, `Tested state`, task-relative paths, mechanical labels, hashes, records, or formal manifests; the deterministic producer owns those fields and maps the machine keys to the canonical labels. If a semantic value cannot be represented by the strict JSON shape, require the complete JSON object with `status: "BLOCKED"`.

Before content reads, implementation, correction, or delegation, manual launches execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> <OPERATION> <SLICE>`. Managed launches execute pathless `node "$STNL_MANAGED_PREFLIGHT"`, which reads the cross-checked context and validates operation/slice, authority, state, and legal recovery. The structural, state, serial-order, requirements-authority, task-schema, active-record, recovery-target, and third-failure gates are deterministic authority. Read the current requirements authority only from the exact `authority=sha256:<64hex>` field returned by that same official preflight, require it to equal the selected artifacts, and copy it byte-identically only into candidate records that carry the authority; the adapter supplies it mechanically to the runner. Never hash `shared/requirements.md`, `feature_spec.md`, or any other raw file, and never reconstruct the canonical authority. When preflight and selected artifacts agree, a different producer-supplied value is not documentary divergence. When preflight blocks, preserve its exact state-derived diagnostic, including the concrete legal operation and slice when present; never substitute values inferred from the current request. Missing or invalid input, an absent slice or artifact, an incomplete serial dependency, an unapproved or stale plan, absent tasks, a concluded slice, an active blocking divergence, an out-of-phase operation, or prior `3/3 TESTS_FAIL` blocks before implementation or correction and therefore before any runner invocation. Once implementation or correction has occurred, the operation cannot end without invoking the configured independent runner.

After implementation or correction, determine the final changed and removed scope and write it to the isolated execution candidate before delegating the runner, without running verification commands in the main context. `Changed Areas` MUST NOT remain the pristine `- pending` sentinel after any file-backed implementation or correction; replace it with every final affected or removed path, or use exact `- none` only for a genuinely fileless operation with an objective fileless reason. Keep the live task unchanged until the complete candidate passes validation and publication. Tests, builds used as verification, linters, typechecks, compilations, validators, contract checks, migration checks, and regression suites are runner-only work.

Start each logical runner invocation in a new independent delegated session with no inherited conversation history, using the configured platform adapter. In managed mode invoke pathless `node "$STNL_MANAGED_RUNNER_BRIDGE"` with only semantic active findings or corrections, current changed scope, compact relevant evidence, the automatic round when applicable, and strictly necessary additional context. Do not repeat adapter, snapshot, bridge, preflight, operation, `SPEC_PATH`, workspace, execution root, slice, plan/task paths, or requirements authority in that payload. The bridge checks freshness and adapter agreement, and the adapter derives and supplies the exact canonical mechanical envelope before dispatch while preserving the semantic payload byte-for-byte. In manual mode use the normal official preflight and configured adapter contract; resolve one canonical existing `SPEC_PATH`, execution root, and concrete plan/task paths without using private-home identity, and require them to remain inside the same managed workspace. Never send conversation history or full logs, and never substitute a source checkout, CWD-relative, candidate, placeholder, or reconstructed path. A missing or mismatched mechanical path is a runtime handoff defect before the runner, not a valid runner `BLOCKED` result. Before accepting any runner status, require each file-backed `Tested state` entry to be task-relative from `dirname(tasks/slice-NN.md)` to its physical target; `src/...`, `test/...`, absolute, CWD-relative, or repository-relative paths are malformed and must never be rebased or accepted. The runner remains read-only over code and execution artifacts.
After deriving each task-relative claim, require the producer to resolve `path.resolve(dirname(taskArtifact), claim)` and compare it by `realpath` with the physical target that will be hashed; claims derived from `SPEC_PATH`, SPEC root, plan, CWD, or workspace root, or claims that omit a task-artifact parent, are malformed and cannot produce `TESTS_PASS`. Do not repair or reinterpret the claim in the runtime.

Invoke the configured independent runner at least once and at most three times within the same manual operation. The first invocation is mandatory after the initial implementation or correction and cannot be skipped because the change appears simple or because no check is expected to apply; the runner performs independent discovery and returns `TESTS_NOT_APPLICABLE` when appropriate. The local invocation budget starts at three for each `EXECUTE_SLICE` or `APPLY_FINDINGS` invocation and is never shared with a later operation. Each successfully started runner request carries the applicable minimum payload and the automatic round as `1/3`, `2/3`, or `3/3`. It returns only the schema for that operation with exactly `TESTS_PASS`, `TESTS_FAIL`, `TESTS_NOT_APPLICABLE`, or `BLOCKED`.

Persist every valid result append-only before deciding what follows. Implementation checks use the next global `implementation-check-NN`; findings checks use the next global `findings-check-NN`. A later manual invocation has its own three-call budget but continues each section's sequence instead of resetting it. Every record includes the automatic round and limit, tested state, verification commands with numeric exit codes, failures, corrections covered, scope, discovery sources and relevant read-only discovery actions, non-applicability rationale, unexpected workspace effects, and compact persistence summary. `TESTS_NOT_APPLICABLE` is valid only after objective discovery and when no verification command was executed; read-only actions used only to discover applicable checks are permitted and recorded under canonical `Discovery sources`.

Classify delegation outcomes before persistence: initialization/transport failure, valid runner `BLOCKED`, malformed runner output, `TESTS_FAIL`, and verification-command failure are distinct. A verification-command failure is represented only by a valid `TESTS_FAIL`; a valid `BLOCKED` is a runner result, not a transport failure.

For an initialization or transport failure only, retry the same logical invocation at most once using a new independent session and the same minimum payload. A shell command that is still running, yielded a session ID, or has not yet delivered its terminal receipt is pending, not an initialization or transport failure: poll that same process/session until it exits and read its final receipt before considering any retry. Do not inspect unrelated processes or start a second runner while the first process is pending. Neither technical start attempt consumes automatic round `1/3`, `2/3`, or `3/3`, creates a `Validation Attempt`, allocates `implementation-check-NN` or `findings-check-NN`, or authorizes a code correction. If the second start also fails, persist exactly one active `Delegation Blocker` singleton with `Kind: initialization` under the selected task's canonical section, both compact transport causes, and the required action, then stop in `RUNNER_INITIALIZATION_BLOCKED`. A malformed response after the runner started is not retried as transport and persists the same singleton with `Kind: malformed-output`, without allocating a check identifier, then stops in `RUNNER_RESULT_BLOCKED`.

When the same stored operation and slice are invoked again from either runner-blocked state, resume directly at the logical runner invocation. This exact persisted delegation recovery remains legal when later formal-validation history exists; it does not reopen implementation or authorize finding correction. Do not reimplement, reapply findings, duplicate checklist or diff summaries, duplicate the blocker, reset global identifiers, or allocate an automatic round or check identifier before a runner session actually starts. If transport fails definitively again, update the existing singleton instead of appending another record. A later valid record resolves it atomically under `references/execution-record-schema.md`.

The operation may end after implementation or correction only after a valid auxiliary status is received or a definitive delegation blocker is persisted. Before a terminal implementation result (`TESTS_PASS`, `TESTS_NOT_APPLICABLE`, or round `3/3 TESTS_FAIL`) is added to the isolated candidate, every mandatory checklist item and its related execution state must already be complete in that same candidate. Candidate validation rejects the inverse ordering. `TESTS_PASS`/`TESTS_NOT_APPLICABLE` then enter `IMPLEMENTED_AWAITING_VALIDATION`; valid runner `BLOCKED` enters `AUXILIARY_BLOCKED`; and round `3/3 TESTS_FAIL` enters `IMPLEMENTATION_RETRY_EXHAUSTED`. Findings outcomes retain their existing `FINDINGS_CORRECTED`, `AUXILIARY_BLOCKED`, and `FINDINGS_RETRY_EXHAUSTED` transitions. Additional automatic rounds occur only after `TESTS_FAIL` in round one or two and an authorized correction. Normally, retry exhaustion permits only explicit `VALIDATE_SLICE` and neither executor operation may re-enter until that formal verdict establishes the next state. Never make a fourth automatic invocation, use an unbounded loop, fall back to checks in the main context, invent a result, implement or correct through the runner, create a Validation Attempt or Effective Validation Base, set a final result, mark `[x]`, or continue automatically to another operation, including `VALIDATE_SLICE`.

One narrow live-state recovery overrides that normal handoff. If the shared runtime finds a terminal implementation result with an incomplete mandatory checklist, it preserves the observed lifecycle state but makes only `EXECUTE_SLICE` for that same slice mandatory, owned by `stnl-slice-executor`, with the concrete implementation record and round. Wrong-slice, validation, replan, and unrelated requests must preserve that target and block. Re-enter only to make the approved implementation/checklist record truthful and complete; preserve the terminal auxiliary record and any formal-validation history, do not allocate another check after a terminal record, and do not modify findings or validation records. Repeated invocation before publication is the same recovery. After candidate validation and one complete selected-task publication, normal validation or retry-exhaustion authority resumes automatically. This is not a generic `IMPLEMENTED_AWAITING_VALIDATION` bypass.

After `TESTS_FAIL` in round one or two, the main context may correct only when the failure evidence objectively identifies a correction inside the approved slice, without changing requirements or strategy, replanning, modifying another slice, or treating an unrelated preexisting failure. Before the next runner invocation, update canonical file-backed `Corrections Applied` path claims; a genuinely fileless correction keeps exact `- none` and uses exact `Correction paths: none` with objective `Fileless reason`, correction rationale, and verification evidence. Persist the reported failure, evidence, applied change, affected files or fileless absence, updated scope, and in-slice rationale in the next auxiliary check's prior-round correction fields. Preserve every earlier check and correction claim.

## EXECUTE_SLICE

Require an open, dependency-ready current-authority slice with approved plans and materialized tasks. Implement only its checklist. Update local checklist items, canonical normalized `Changed Areas` path claims, discovered expansion, divergences, and a compact diff summary in the isolated candidate. For every file-backed execution-record field defined as task-relative, derive the stored path from the selected final live task artifact itself: `path.relative(dirname(tasks/slice-NN.md), physicalTarget)`, normalized to `/`. The prepared candidate task has exactly the same depth as that live task, so the claim resolves to the same physical target from either path. This applies to executor-owned `Changed Areas` and `Corrections Applied` and to persisted runner-owned `Tested state` or correction-path output. Never derive those values from the process CWD, workspace root, repository root, or SPEC root; never repair or reinterpret an incorrectly based producer value. Persist every divergence under local `references/execution-record-schema.md`; newly detected blocking divergences are `Severity: blocking`, `State: active`, and direct first to lifecycle `RESUME` when documentary authority must change, then to `REPLAN`. The executor never resolves or supersedes a divergence. Verify every mandatory checklist item complete in the candidate before delegating checks, then append the result under `Implementation Test Evidence` as the next `implementation-check-NN`, including status, tested state, commands and numeric exit codes, selected tests, selection rationale, coverage, compact evidence or failure summary, blockers, unexpected workspace effects, and persistence summary. The only exception is the narrow existing-inconsistency recovery above, where a terminal implementation record already exists and must be preserved.

For every file-backed `Tested state`, the deterministic producer hashes the physical target and inserts the complete lowercase digest with 64 hex characters into the isolated candidate. Never hand-type, truncate, abbreviate, or substitute a digest; do not manually copy it from command output. If candidate validation rejects a generated record, distinguish producer failure from a candidate transcription or layout error; preserve the rejected candidate and regenerate a fresh candidate from unchanged live authority and the same valid semantic response when the code and tested state are unchanged.
Keep the absolute `RUNNER_EVIDENCE_SERIALIZER` local to this skill for candidate persistence; do not copy that path, or any concrete serializer path, into the delegated runner prompt. The platform adapter supplies exactly one canonical serializer authority from the frozen snapshot, along with the canonical managed workspace derived from the official `SPEC_PATH` and its Git root, and the exact `SPEC_PATH` and `SLICE`. For `EXECUTE_SLICE` and `APPLY_FINDINGS`, the delegated runner returns one raw JSON object containing only model-owned lowerCamelCase semantic fields and exact `{command, exit}` command objects; it does not emit `Operation`, `Tested scope`, `Tested state`, mechanical labels, hashes, or record sections. The main execution context writes that JSON unchanged to a temporary file outside the SPEC and invokes exactly once `node "$RUNNER_EVIDENCE_SERIALIZER" --execution-bundle --operation <requested-operation> --workspace <managed workspace> --task-artifact <candidateTaskArtifact> --semantic-response-file <absolute-temp-file> --insert-candidate`. The candidate task is the same-depth sibling returned by `prepare-execution-copy.mjs`, with completed `Changed Areas` and applicable `Corrections Applied`; never use `--spec-path` for this execution bundle because that selects the still-pristine live task. Before deriving physical targets, the producer canonicalizes `Changed Areas` and `Corrections Applied` from the approved `Checklist` expected-area physical targets into `path.relative(dirname(taskArtifact), target)` claims; it accepts a workspace-relative alias only when it maps uniquely to one approved target and blocks ambiguous or unresolvable claims. It then derives physical targets from those canonical sections, verifies physical identity, computes task-relative `path.relative`, normalizes `/`, orders claims and commands, emits every literal label/delimiter and complete SHA-256, and inserts the complete canonical `### implementation-check-NN` or `### findings-check-NN` record into the selected section of the owned isolated candidate. The main context does not transcribe hashes, tuples, labels, or the record and does not remap response-oriented labels. A nonzero producer exit blocks publication of that candidate; preserve its diagnostic. When the defect is correctable under unchanged official authority, create a fresh candidate from live, apply the correction and the same valid semantic runner response only if the code and tested state are unchanged, then rerun the producer before candidate validation. Never repair a rejected candidate after validation. `VALIDATE_SLICE` uses the analogous semantic boundary with `--validation-bundle --semantic-response-file`; it derives `Type` from execution-state, injects `Operation`, and owns the canonical field order. Neither operation invokes legacy `--record` or `--response` from the delegated runner.

The platform adapter owns raw-response capture. If it returns an absolute semantic response file, pass that file byte-for-byte to the deterministic evidence producer and do not invoke a second capture. If it returns only structured JSONL output, capture it with the exact absolute `capture-runner-response.mjs` helper path resolved from this skill root, using `--structured-output-file <absolute-runner-output> --output <absolute-temp-file>`. The capture helper extracts the final `agent_message` and writes its JSON object byte-for-byte; it rejects invalid JSON, arrays, JSON string literals, and absent messages. Do not use shell quoting, `JSON.stringify`, `jq -R`, manual unwrapping, or post-rejection repair. The capture helper owns only response-file materialization; the existing serializer remains the strict producer and candidate validation remains authoritative.
Before accepting `TESTS_PASS`, require the producer to insert each file-backed digest as exactly `sha256:` plus 64 lowercase hexadecimal characters and require strict candidate validation. A genuinely malformed semantic response remains `RUNNER_RESULT_BLOCKED`; a producer or candidate insertion failure is diagnosed from its own exit and must not be mislabeled as runner output.
Every file-backed `Tested state` tuple must use the literal `sha256:` delimiter; `sha256=` or any other separator is malformed output and remains `RUNNER_RESULT_BLOCKED`.
The deterministic producer's serialized tuple forms are exact: each file-backed `Tested state` line is `- \`<task-relative path>\` | sha256:<64 lowercase hex>` or `- \`<task-relative path>\` | REMOVED`, and each semantic runner `Commands` line is `- \`<full command>\` | exit:<integer>`. Pipe, backticks, the literal `sha256:`/`REMOVED`, and `exit:` marker are mandatory in the respective producer output; the runner does not manufacture the file-backed tuple.
When classifying runner output, if the official preflight, payload, and selected artifact carry the same canonical authority token, discard any raw requirements-file SHA mentioned by the response; never copy, compare, report it as a divergence, or block because of it. Only a missing or unequal official token may block authority. A genuinely malformed runner schema remains `RUNNER_RESULT_BLOCKED` for that schema defect.

Compare every changed path with the Effective Validation Bases of earlier completed slices. Record each overlap under `Prior Validation Overlap` with the earlier slice, affected behavior, and regressions the current validation must justify. The model may use the compact semantic carrier `- Slice NN overlap: <path claims>; <behavior and regression rationale>`; the validation producer extracts only those physical path claims and serializes the canonical evidence deterministically. Include the path in the current slice's changed areas. Do not reopen or rewrite an earlier slice.

On `TESTS_FAIL` before the third round, apply only an objectively supported in-scope correction, update changed scope, record the correction, and invoke the runner again within the same `EXECUTE_SLICE`. If that correction is not authorized, append the applicable active blocking divergence and stop. On the third `TESTS_FAIL`, persist evidence, enter `IMPLEMENTATION_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist discovery sources, relevant read-only discovery actions, verification types considered, objective rationale, and confirmation that no verification command was executed. On `BLOCKED`, record the cause and required action and enter `AUXILIARY_BLOCKED`. Every status leaves the slice open and formal validation pending; no check creates a formal finding or invokes another operation automatically.

## APPLY_FINDINGS

Require at least one persisted active blocking finding in `VALIDATION_NEEDS_FIX`, and reject retry-exhausted or already-corrected phases. Read active findings, the selected plan and task record, affected code and tests, and necessary requirements. Correct only reported problems and their necessary effects. For file-backed work, add every final affected or removed path to canonical `Changed Areas` and `Corrections Applied`, deriving each stored value with `path.relative(dirname(tasks/slice-NN.md), physicalTarget)` from the selected final task artifact and normalizing separators to `/`. Persist runner-owned `Tested state` and correction paths on that same basis. For a genuinely fileless correction, keep both sections exact `- none`, never invent a path/hash, and persist objective reason, correction rationale, and verification evidence in the existing check fields. Preserve all finding records, Validation Attempts, and any historical Effective Validation Base until later formal validation; correction and auxiliary checks never change finding state.

Then delegate checks automatically and append the result under `Findings Test Evidence` as the next `findings-check-NN`, associated with the applicable findings cycle. `Finding IDs` is the canonical target set; `Findings verified` is a canonical subset (or `none`); `Unsupported active findings` is every active finding in that cycle not verified by the check. In addition to those sets, record corrections covered and regressions selected.

On `TESTS_FAIL` before the third round, adjust only persisted active findings, failures introduced or exposed by their corrections, directly related regressions, and necessary effects inside approved scope. Update corrections and changed scope, record the between-round correction, and invoke the runner again within the same `APPLY_FINDINGS`. On the third `TESTS_FAIL`, persist evidence, leave every previously active finding active while preserving historical states, enter `FINDINGS_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist objective discovery, relevant read-only discovery actions, verification types considered, rationale, and confirmation that no verification command was executed without resolving findings. On `BLOCKED`, preserve cause and required action and enter `AUXILIARY_BLOCKED`. Do not perform formal validation, mark completion, set final result, replace prior Validation Attempts or Effective Validation Base, or invoke `VALIDATE_SLICE` automatically. If correction requires a requirement, scope, dependency, or strategy change, append an active blocking divergence and direct first to lifecycle `RESUME` when needed and then explicit `REPLAN`.

## Execution artifact publication

Never append or replace a live execution record directly. Run `node "<SKILL_ROOT>/runtime/prepare-execution-copy.mjs" --prepare --spec-path <SPEC_PATH> --slice <SLICE>` to copy the complete execution tree to its owned same-depth sibling outside the SPEC and inside the managed workspace. Apply only executor-owned changes to `candidateTaskArtifact`, pass that exact artifact to the execution evidence producer, then execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --candidate <CANDIDATE_EXECUTION_ROOT>`. This invocation and publication ownership are contract/model enforced; the runtime enforces strict candidate parsing when called, rejects terminal implementation evidence paired with an incomplete checklist, but is not a publisher and does not authorize the diff. A rejected candidate consumes no additional runner call, check round, identifier, or live history. Preserve the rejected candidate and exact diagnostic. If the cause is correctable under unchanged official authority, create a new candidate from live, apply the diagnosed correction, validate it strictly, and publish only that valid new proposal; never mutate or republish the rejected candidate. After candidate PASS, run `node "<SKILL_ROOT>/runtime/prepare-execution-copy.mjs" --publish --spec-path <SPEC_PATH> --slice <SLICE> --candidate-root <candidateRoot>`; the helper rechecks unchanged live authority and candidate validity, atomically replaces only the selected task, and removes only its owned successful candidate. Never expose the checklist and terminal implementation record as separate live writes. Then execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after <OPERATION>` as the strict readback before declaring the record persisted. Treat this readback as read-only: require exit zero and inspect the resulting state, normal handoff, legal operations, required recovery handoff, and mandatory same-operation recovery; block on a nonzero exit, malformed output, or reported contract diagnostic. Do not repeat the original operation preflight: it authorized work in the initial state and may correctly reject that operation after publication.

## Allowed Effects

- modify implementation and tests inside the selected scope;
- after implementation or correction, invoke the configured independent runner at least once and no more than three times in the selected manual operation;
- update only execution-owned sections of `tasks/slice-NN.md`, including the appropriate append-only test-evidence section.
- use temporary support files only in an external operating-system temporary directory; never create scratch files, scripts, manifests, or ad hoc reports inside the SPEC or execution root.

## Blocks

Block missing or invalid inputs, absent artifacts, incomplete dependencies, stale requirements authority, a concluded slice, an active blocking divergence, either normally consistent retry-exhausted state, out-of-scope work, a required planning/requirements decision, a non-canonical execution path or unsafe reserved SPEC entry reported by preflight, unavailable or malformed runner behavior after the bounded transport policy and objective persistence above, or an attempt to mutate plans, the global task index, another slice, or a concluded slice. The exact checklist-inconsistency and persisted same-operation delegation recoveries above are the only exceptions to the normal phase/history gates. Arbitrary lifecycle-external or user-owned SPEC-root siblings are allowed and preserved. Report each blocking path exactly and require relocation or explicit removal; never delete it automatically.

## Output

After persistence, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after <OPERATION>` and report its normal handoff, every legal operation, required recovery handoff, and mandatory same-operation recovery as separate fields. Also report operation, selected slice, changed areas, delegated-check status and evidence location, divergences, and candidate/read-back validation. Stop.
