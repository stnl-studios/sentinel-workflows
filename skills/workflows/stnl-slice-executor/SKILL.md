# stnl-slice-executor

## Purpose

Run exactly one manual operation: `EXECUTE_SLICE` or `APPLY_FINDINGS`. Work on one explicit normalized slice, delegate every applicable test or verification command to the configured validation runner, persist only compact evidence, and stop before formal validation or global completion. A manual operation may contain a bounded automatic correction-and-recheck cycle; it never creates another manual operation.

## Inputs

- `SPEC_PATH`: required. A directory must contain `feature_spec.md` and uses its `execution/` child; that file path resolves identically; another requirements file uses sibling `<stem>-execution/`. Block every other form.
- `SLICE`: required and explicit. Accept one unsigned decimal number and normalize it to `slice-NN`; never infer it.
- Optional additional context may narrow the selected operation but cannot expand approved scope.
- Optional `BYPASS_GATE=<prior-record-NN>/gate-NN` plus `BYPASS_REASON=<accepted risk>` targets only that optional gate; revalidate before evaluating explicit operator acceptance under the shared record contract.
- The launcher supplies the platform-specific runner invocation. This skill contains no vendor-specific invocation syntax.

## Authority

Current requirements authority and approved plans define scope. `tasks.md` defines global progress and is read-only for this skill. The selected detailed task file authorizes local work and records execution. Its `Requirements authority` and `Plan revision` must match the current open slice and deterministic preflight. The configured independent runner owns discovery and the logical plan, plus later assessment only when Gate interpretation is required. The packaged harness owns physical execution and sealed evidence. This skill owns implementation, candidate composition and authorized publication; it never invents or repairs harness fields.

Execution preflight is read-only. An accepted mandatory resume includes a structured `MANDATORY_RECOVERY` record; an incompatible request includes structured `RECOVERY_TARGETS`. Preserve those fields exactly. Only when preflight reports a mechanical violation for the exact `Findings IDs` alias or the exact historical `Check discovery sources` / `Check discovery actions` pair may this skill explicitly run `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --repair-known-contract` once and repeat the original preflight; every other contract violation blocks.

## Minimum Reads

- `plan.md`, `tasks.md`, selected detailed plan and task file;
- requirements referenced by the selected slice;
- local `references/execution-record-schema.md` before persisting or interpreting findings, divergences, checks, or supersession;
- directly related code, tests, imports, dependencies, and prior compact test evidence only.

## Delegated Checks

Before content reads, implementation, correction, or delegation, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> <OPERATION> <SLICE>`. Its structural, state, serial-order, requirements-authority, task-schema, active-record, recovery-target, and third-failure gates are deterministic authority. When it blocks, preserve its exact state-derived diagnostic, including the concrete legal operation and slice when present; never substitute values inferred from the current request. Missing or invalid input, an absent slice or artifact, an incomplete serial dependency, an unapproved or stale plan, absent tasks, a concluded slice, an active blocking divergence, an out-of-phase operation, or prior `3/3 TESTS_FAIL` blocks before implementation or correction and therefore before any runner invocation. Once implementation or correction has occurred, the operation cannot end without invoking the configured independent runner.

After implementation or correction, determine the final changed and removed scope without running verification commands in the main context. Invoking the packaged Sentinel bridge is authorized orchestration, not direct toolchain execution. The runner discovers and plans logical verification only. Tests, builds used as verification, linters, typechecks, compilations, validators, contract checks, migration checks, and regression suites are physically executed only by the packaged harness through the owning skill resolver; neither main context nor runner may spawn them directly.

Start each logical runner invocation in a new independent delegated session with no inherited conversation history, using the platform launcher supplied by the caller. Send only operation, `SPEC_PATH`, selected slice, current requirements fingerprint and plan revision, applicable active findings or corrections, current changed scope, compact relevant evidence, automatic round when applicable, references necessary for project discovery, and strictly necessary additional context. Never send the loaded skill root, installation path, resolver/runtime filename, harness path, packaged schema path, secret infrastructure value, conversation history or full logs. The runner remains read-only and returns one `stnl-validation-plan/v1` object, not TESTS_PASS, counts, exits or provenance.

Invoke the configured independent runner at least once and at most three times within the same manual operation. The first planning invocation is mandatory after the initial implementation or correction and cannot be skipped because the change appears simple or because no check is expected to apply. The local invocation budget starts at three for each operation and is never shared with a later operation. Each successfully started request carries the automatic round as `1/3`, `2/3`, or `3/3`. A plan with no verification commands is not success: it requires objective discovery and non-applicability rationale, both validated by the bridge.

Immediately reject result-shaped planner output (`TESTS_PASS`, PASS/BLOCKED text, exit/test counts, stdout or provenance) before any harness-result or candidate handling. After receiving a plan, the owner invokes this exact installed entrypoint relative to the already-loaded `SKILL.md`:

`node "<SKILL_ROOT>/runtime/resolve-validation-runtime.mjs" --execute-plan <SPEC_PATH> '<PLAN_JSON>'`

`<SKILL_ROOT>` is the loaded resource location, never cwd, HOME, an installation convention, operator input or delegated data. At this moment the bridge validates schema, owner operation, capability, authority, revision, slice, round, lifecycle, explicit environment and bounded outputs; obtains prior evidence from current lifecycle; resolves its own harness from `import.meta.url`; performs handshakes; builds the low-level request; and invokes the harness. Missing `executionEnvironment` blocks before dispatch and never defaults to host.

The command returns only a compact summary plus `resultFile`; the sealed envelope and logs remain in that owner-private OS-temporary receipt. Do not open, decode, copy or reserialize it. After composing the checklist/diff/correction sections in an isolated candidate, invoke `node "<SKILL_ROOT>/runtime/resolve-validation-runtime.mjs" --stage-candidate <SPEC_PATH> <resultFile> <CANDIDATE_EXECUTION_ROOT>`. That specific helper inserts the bridge-derived record and untouched opaque envelope, resolves a matching historical Delegation Blocker when applicable, and runs candidate validation. The owner then publishes only the already-accepted authorized paths and confirms read-back. A raw accepted plan or summary cannot be staged as success.

Persist every bridge-produced result append-only before deciding what follows. Implementation checks use the next global `implementation-check-NN`; findings checks use the next global `findings-check-NN`. A later manual invocation continues each section's sequence. `TESTS_NOT_APPLICABLE` is valid only after an accepted empty plan with objective discovery and a sealed harness envelope confirming that no verification command executed.

Classify delegation outcomes before persistence: initialization/transport failure, authenticated harness pre-check infrastructure/source-isolation `BLOCKED`, evidence-bearing runner `BLOCKED`, malformed runner output, `TESTS_FAIL`, and verification-command failure are distinct. A verification-command failure retains its raw exit and is classified by the shared Gate assessments contract. An authenticated pre-check block has exact `INVALID/INFRASTRUCTURE_BLOCKED/NONE` provenance, no commands, and no isolated workspace; it is a valid runner result but has not entered check execution.

For an initialization or transport failure only, retry the same logical invocation at most once using a new independent session and the same minimum payload. Neither technical start attempt consumes automatic round `1/3`, `2/3`, or `3/3`, creates a `Validation Attempt`, allocates `implementation-check-NN` or `findings-check-NN`, or authorizes a code correction. If the second start also fails, persist exactly one active `Delegation Blocker` singleton with `Kind: initialization` under the selected task's canonical section, both compact transport causes, and the required action, then stop in `RUNNER_INITIALIZATION_BLOCKED`. A malformed response after the runner started is not retried as transport and persists the same singleton with `Kind: malformed-output`, without allocating a check identifier, then stops in `RUNNER_RESULT_BLOCKED`. A contract-valid harness pre-check infrastructure/source-isolation block is not malformed and does not receive a transport retry: persist its exact `HEAD`, `Evidence provenance`, and authenticated code/message in the singleton with `Kind: infrastructure`, allocate no check identifier, preserve the pending round, and stop in `RUNNER_RESULT_BLOCKED`.

When the same stored operation and slice are invoked again from either runner-blocked state, resume directly at the logical runner invocation. This exact persisted delegation recovery remains legal when later formal-validation history exists; it does not reopen implementation or authorize finding correction. Do not reimplement, reapply findings, duplicate checklist or diff summaries, duplicate the blocker, reset global identifiers, or allocate an automatic round or check identifier before a runner session actually starts. If transport fails definitively again, update the existing singleton instead of appending another record. A later valid record resolves it atomically under `references/execution-record-schema.md`.

The operation may end after implementation or correction only after a valid auxiliary status is received or a definitive delegation blocker is persisted. Before a terminal implementation result (`TESTS_PASS`, `TESTS_ACCEPTED`, `TESTS_NOT_APPLICABLE`, or round `3/3 TESTS_FAIL`) is added to the isolated candidate, every mandatory checklist item and its related execution state must already be complete in that same candidate. Candidate validation rejects the inverse ordering. `TESTS_PASS`/`TESTS_ACCEPTED`/`TESTS_NOT_APPLICABLE` then enter `IMPLEMENTED_AWAITING_VALIDATION`; an evidence-bearing runner `BLOCKED` after check entry enters `AUXILIARY_BLOCKED`; an authenticated pre-check infrastructure block remains outside auxiliary records in `RUNNER_RESULT_BLOCKED`; and round `3/3 TESTS_FAIL` enters `IMPLEMENTATION_RETRY_EXHAUSTED`. Findings outcomes retain their existing `FINDINGS_CORRECTED`, `AUXILIARY_BLOCKED`, and `FINDINGS_RETRY_EXHAUSTED` transitions. Additional automatic rounds occur only after `TESTS_FAIL` in round one or two and an authorized correction. Normally, retry exhaustion permits only explicit `VALIDATE_SLICE` and neither executor operation may re-enter until that formal verdict establishes the next state. Never make a fourth automatic invocation, use an unbounded loop, fall back to checks in the main context, invent a result, implement or correct through the runner, create a Validation Attempt or Effective Validation Base, set a final result, mark `[x]`, or continue automatically to another operation, including `VALIDATE_SLICE`.

One narrow live-state recovery overrides that normal handoff. If the shared runtime finds a terminal implementation result with an incomplete mandatory checklist, it preserves the observed lifecycle state but makes only `EXECUTE_SLICE` for that same slice mandatory, owned by `stnl-slice-executor`, with the concrete implementation record and round. Wrong-slice, validation, replan, and unrelated requests must preserve that target and block. Re-enter only to make the approved implementation/checklist record truthful and complete; preserve the terminal auxiliary record and any formal-validation history, do not allocate another check after a terminal record, and do not modify findings or validation records. Repeated invocation before publication is the same recovery. After candidate validation and one complete selected-task publication, normal validation or retry-exhaustion authority resumes automatically. This is not a generic `IMPLEMENTED_AWAITING_VALIDATION` bypass.

After `TESTS_FAIL` in round one or two, the main context may correct only when the failure evidence objectively identifies a correction inside the approved slice, without changing requirements or strategy, replanning, modifying another slice, or treating an unrelated preexisting failure. Before the next runner invocation, update canonical file-backed `Corrections Applied` path claims; a genuinely fileless correction keeps exact `- none` and uses exact `Correction paths: none` with objective `Fileless reason`, correction rationale, and verification evidence. Persist the reported failure, evidence, applied change, affected files or fileless absence, updated scope, and in-slice rationale in the next auxiliary check's prior-round correction fields. Preserve every earlier check and correction claim.

## Current-state revalidation

Read the Quality gate observations, revalidation and acceptance contract in `references/execution-record-schema.md` for every failed command or resume. Revalidate old conditions against current working-tree bytes, including manual/external fixes without commit. Auxiliary BLOCKED resumes directly at its runner; do not repeat completed implementation. APPLY_FINDINGS first inspects whether the finding still exists; if already corrected, delegate current checks without inventing changes and report provenance in existing evidence. Independent external failures never authorize fixes or a divergence. Raw nonzero exits may coexist with TESTS_PASS only through complete non-blocking assessments; a granular explicitly authorized optional gate bypass requires TESTS_ACCEPTED and remains distinct from formal completion. Revalidate all bypasses again in formal validation.

## EXECUTE_SLICE

Require an open, dependency-ready current-authority slice with approved plans and materialized tasks. Implement only its checklist. Update local checklist items, canonical normalized `Changed Areas` path claims, discovered expansion, divergences, and a compact diff summary. Persist every divergence under local `references/execution-record-schema.md`; newly detected blocking divergences are `Severity: blocking`, `State: active`, and direct first to lifecycle `RESUME` when documentary authority must change, then to `REPLAN`. The executor may resolve an obsolete observational divergence only through fresh Gate assessments and the existing record resolution contract; it never changes documentary authority or supersedes a divergence. Verify every mandatory checklist item complete before delegating checks, then append the result under `Implementation Test Evidence` as the next `implementation-check-NN`, including status, tested state, commands and numeric exit codes, selected tests, selection rationale, coverage, compact evidence or failure summary, blockers, unexpected workspace effects, and persistence summary. The only exception is the narrow existing-inconsistency recovery above, where a terminal implementation record already exists and must be preserved.

Compare every changed path with the Effective Validation Bases of earlier completed slices. Record each overlap under `Prior Validation Overlap` with the earlier slice, affected behavior, and regressions the current validation must justify. Include the path in the current slice's changed areas. Do not reopen or rewrite an earlier slice.

On `TESTS_FAIL` before the third round, apply only an objectively supported in-scope correction, update changed scope, record the correction, and invoke the runner again within the same `EXECUTE_SLICE`. If the failure is independent external debt, record non-blocking Gate assessments. Unknown relevance is temporary BLOCKED for investigation. Only proven relevant authority expansion with no valid in-scope correction creates an active blocking divergence; an external path alone cannot justify it. On the third `TESTS_FAIL`, persist evidence, enter `IMPLEMENTATION_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist discovery sources, relevant read-only discovery actions, verification types considered, objective rationale, and confirmation that no verification command was executed. On `BLOCKED`, record the cause and required action and enter `AUXILIARY_BLOCKED`. Every status leaves the slice open and formal validation pending; no check creates a formal finding or invokes another operation automatically.

## APPLY_FINDINGS

Require at least one persisted active blocking finding in `VALIDATION_NEEDS_FIX`, and reject retry-exhausted or already-corrected phases. Read active findings, the selected plan and task record, affected code and tests, and necessary requirements. Correct only reported problems and their necessary effects. For file-backed work, add every final affected or removed path to canonical `Changed Areas` and `Corrections Applied`. For a genuinely fileless correction, keep both sections exact `- none`, never invent a path/hash, and persist objective reason, correction rationale, and verification evidence in the existing check fields. Preserve all finding records, Validation Attempts, and any historical Effective Validation Base until later formal validation; correction and auxiliary checks never change finding state.

Then delegate checks automatically and append the result under `Findings Test Evidence` as the next `findings-check-NN`, associated with the applicable findings cycle. `Finding IDs` is the canonical target set; `Findings verified` is a canonical subset (or `none`); `Unsupported active findings` is every active finding in that cycle not verified by the check. In addition to those sets, record corrections covered and regressions selected.

On `TESTS_FAIL` before the third round, adjust only persisted active findings, failures introduced or exposed by their corrections, directly related regressions, and necessary effects inside approved scope. Update corrections and changed scope, record the between-round correction, and invoke the runner again within the same `APPLY_FINDINGS`. On the third `TESTS_FAIL`, persist evidence, leave every previously active finding active while preserving historical states, enter `FINDINGS_RETRY_EXHAUSTED`, and report explicit `VALIDATE_SLICE` as the only next slice action; do not correct again or permit executor re-entry. On `TESTS_NOT_APPLICABLE`, persist objective discovery, relevant read-only discovery actions, verification types considered, rationale, and confirmation that no verification command was executed without resolving findings. On `BLOCKED`, preserve cause and required action and enter `AUXILIARY_BLOCKED`. Do not perform formal validation, mark completion, set final result, replace prior Validation Attempts or Effective Validation Base, or invoke `VALIDATE_SLICE` automatically. If correction requires a requirement, scope, dependency, or strategy change, append an active blocking divergence and direct first to lifecycle `RESUME` when needed and then explicit `REPLAN`.

## Execution artifact publication

Never append or replace a live execution record directly. Copy the complete execution tree to an isolated operating-system temporary candidate, apply only executor-owned changes there, and execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --candidate <CANDIDATE_EXECUTION_ROOT>`. This invocation and publication ownership are contract/model enforced; the runtime enforces strict candidate parsing when called, rejects terminal implementation evidence paired with an incomplete checklist, but is not a publisher and does not authorize the diff. A rejected candidate consumes no additional runner call, check round, identifier, or live history. Publish the complete selected task artifact as one replacement only after successful candidate validation; never expose the checklist and terminal implementation record as separate live writes. Then strictly read back through the original preflight before declaring the record persisted.

## Allowed Effects

- modify implementation and tests inside the selected scope;
- after implementation or correction, invoke the configured independent runner at least once and no more than three times in the selected manual operation;
- update only execution-owned sections of `tasks/slice-NN.md`, including the appropriate append-only test-evidence section.
- use temporary support files only in an external operating-system temporary directory; never create scratch files, scripts, manifests, or ad hoc reports inside the SPEC or execution root.

## Blocks

Block missing or invalid inputs, absent artifacts, incomplete dependencies, stale requirements authority, a concluded slice, a still-valid blocking divergence after revalidation, either normally consistent retry-exhausted state, out-of-scope work, a required planning/requirements decision, a non-canonical execution path or unsafe reserved SPEC entry reported by preflight, unavailable or malformed runner behavior after the bounded transport policy and objective persistence above, or an attempt to mutate plans, the global task index, another slice, or a concluded slice. The exact checklist-inconsistency and persisted same-operation delegation recoveries above and the runtime-selected observational blocker revalidation are the exceptions to the normal phase/history gates. Arbitrary lifecycle-external or user-owned SPEC-root siblings are allowed and preserved. Report each blocking path exactly and require relocation or explicit removal; never delete it automatically.

## Output

After persistence, execute `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after <OPERATION>` and report its normal handoff, every legal operation, required recovery handoff, and mandatory same-operation recovery as separate fields. Also report operation, selected slice, changed areas, delegated-check status and evidence location, divergences, and candidate/read-back validation. Stop.
