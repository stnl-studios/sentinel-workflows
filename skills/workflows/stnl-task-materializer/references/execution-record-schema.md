# File Purpose Header

```yaml
purpose: Define operational task-record schemas that must never appear in a freshly materialized pristine task.
status: not_applicable
read_when: EXECUTE_SLICE, APPLY_FINDINGS, VALIDATE_SLICE, REPLAN materialization, or CLOSE persists or interprets operational records.
do_not_read_when: Only a pristine task is being rendered or reviewed.
contains: Check evidence, findings, divergences, attempts, supersession, effective validation base, and lifecycle transitions.
owner: stnl-task-materializer
update_policy: Change only when persisted execution-record identity or lifecycle semantics change.
```

# Execution Record Schema

Fresh materialization contains only its exact section sentinels (`- none` or `- pending`). The headings below are operational records, never template examples and never pristine placeholders.

Every newly materialized task, pristine replacement, and append-only recovery task carries exact `- Validation evidence contract: stnl-validation-evidence/v1` under References. Existing historical tasks without the marker remain readable under the legacy contract and are not silently retrofitted. Once present, the marker cannot be removed or downgraded. Every new auxiliary check or formal attempt in a v1 task requires structured Evidence provenance emitted by the bundled validation harness under `stnl-validation-runner/v10` ↔ `stnl-validation-harness/v10` and the current loaded validation capability identity. Historical v1 provenance emitted before protocol/receipt/capability, explicit `executionEnvironment`, authenticated external-toolchain, or live-delta fields existed remains readable only to preserve lifecycle/recovery state; it cannot authorize a new execution, be appended as a new record, or be used as a replay origin. Historical-read compatibility is never operational compatibility.

## Strict write check and exact contract repair

The parser accepts only canonical `Finding IDs`, `Discovery sources`, and `Discovery actions`. The model-authored execution-record writer contract requires an isolated candidate and the bundled `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --candidate <CANDIDATE_EXECUTION_ROOT>` before publication. That invocation and mutation ownership are contract/model enforced; when invoked, the runtime strictly parses the complete candidate and compares persisted task history against live artifacts without changing live execution. It is not a generic publisher and does not prove an authorized diff.

Every preflight is read-only. When its structured violation identifies either exact `Findings IDs` or the exact historical pair `Check discovery sources` / `Check discovery actions`, no canonical field coexists, every required legacy field occurs once with a non-empty value, and any finding IDs pass the current grammar and membership rules, the caller may explicitly run `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --repair-known-contract`. The runtime collects every approved occurrence in that one task artifact and changes only approved labels in a complete isolated candidate. Publication acquires a repair-local exclusive lock, revalidates source identity and bytes, claims the source into an owned backup, installs the candidate with no-replace semantics, strictly reads it back, and rolls back only while the live publication is still repair-owned. A concurrent source or lock replacement aborts without overwriting or removing foreign bytes. If another task artifact also requires repair, the operation blocks because multi-file replacement is not authorized. Duplicates, coexistence, incomplete pairs, unknown labels, undeclared/invalid values, or any other invalidity remain blocked. Repair changes no value, semantic record, owner, attempt, round, validation base, runner budget, product code, or test result; it is not a generic publisher.

Only complete historical producer signatures receive legacy classification. The exact `e45e41d` split-plan producer requires its historical File Purpose Header values plus exact primary H1, ordered sections, authority-field layout, and canonical table shape; it predates `Requirements authority` and `Plan revision` and is semantically incomplete. The exact `98545e4` lifecycle-root phase generation, identified by its historical owners, primary H1s, sections, tables, filenames, and paired details, is structurally incompatible. Both remain blocked because the runtime cannot invent authority or migrate history. An old H1 in prose/fenced text, missing current authority fields, a hybrid structure, or editorial `tasks.md` prose is a current parse concern, never a historical signature. No broad migration is attempted.

## Changed and corrected paths

After work starts, `Changed Areas` replaces `- pending` with a non-empty lexicographically ordered list of unique normalized task-relative paths, each exactly `- \`<path>\``. The only exception is exact `- none` when the current state-driving auxiliary check uses `Tested state: none` plus objective `Fileless reason`, and later for its terminal fileless PASS whose Effective Validation Base uses `Files: none` with an objective `Fileless reason`; it never authorizes an invented path. Current file-backed evidence requires paths, while older fileless/file-backed rounds remain valid when the current authority is coherent. `Corrections Applied` remains `- none` or uses the same list format; fileless APPLY_FINDINGS may keep exact `- none` with objective correction evidence. Every file-backed corrected path must also occur in `Changed Areas`. Nested bullets, prose, absolute paths, backslashes, duplicate paths, and unnormalized paths are invalid. `REMOVED` versus SHA-256 ownership is recorded in the Effective Validation Base; these sections claim the affected path without duplicating that disposition.

## Findings and divergences

Identifiers are append-only and sequential within their section. Never reuse, renumber, remove, or mutate the identity or origin of a historical record.

`validateExecutionCandidate` enumerates live task artifacts and compares each existing record by slice and identifier. Only an active finding or divergence may change `State` and add the canonical `Resolution` or `Superseded by` allowed by the final-state lifecycle checks. Every other original field remains unchanged, including Severity, Origin, Kind, Required authority operation, Problem, Evidence, and additional historical fields. Omitted legacy Kind remains omitted and conservatively means authority; revalidation cannot add observational Kind or change RESUME to REPLAN (or the reverse). Already resolved/superseded dispositions are immutable. Materialized REPLAN retains its disposition authority and cannot rewrite original identity.

The same comparison preserves complete prior attempts/checks and their gate/bypass history, operational task authority references, and terminal tasks including their Effective Validation Base, exact result, and supersession owner. An existing delegation singleton may change only active State to resolved and add Resolution; its original operation, kind, anchor, causes and required action remain unchanged. Removing a record or its whole operational task is rejected. Pristine replacement has no operational history to preserve. A divergence resolution must reference a newly appended revalidation record, whose snapshots are checked against the working tree; a historical observation cannot authorize a new disposition. Publication remains model-owned and must use the validated candidate followed by strict readback.

```markdown
### finding-NN

- Severity: blocking|advisory
- State: active|resolved|superseded
- Origin: <operation/attempt>
- Kind: implementation_defect|code_regression
- Evidence identity: sha256:<64 lowercase hexadecimal characters>
- Problem: <compact problem>
- Evidence: <compact objective evidence>
- Impact: <requirement or behavior impact>
- Related authority: <requirement/plan/task references>
- Expected correction: <objective correction>
```

```markdown
### divergence-NN

- Severity: blocking|advisory
- State: active|resolved|superseded
- Origin: <operation/attempt>
- Problem: <compact authority/scope/strategy divergence>
- Evidence: <compact objective evidence>
- Kind: observational|authority|structural|required
- Required authority operation: <none for observational; RESUME or REPLAN otherwise>
```

An active record omits both disposition fields. A resolved record adds only `- Resolution: <non-placeholder resolution>`. A superseded record adds only `- Superseded by: <strictly later same-kind identifier>`.

Every finding created by a `NEEDS_FIX` attempt is born `active`. Every valid later formal `VALIDATE_SLICE` attempt owns deterministic per-finding dispositions. A later `NEEDS_FIX` attempt may resolve fully corrected prior findings, supersede a finding with a new same-kind finding whose origin is strictly later, leave still-failing findings active, and append new active findings. A current `PASS` must atomically resolve or supersede every remaining active blocking finding before completion; `ACCEPTED` may retain only findings with an exact current optional gate bypass. Each resolution names a formal attempt strictly later than the origin. `APPLY_FINDINGS`, partial correction, and auxiliary checks never resolve or supersede findings.

The atomic `MATERIALIZE_TASKS` commit of an approved `REPLAN` may change applicable active divergences to `resolved` or `superseded`. The separate revalidation resolution below permits the original operation owner to resolve an obsolete observation without changing authority. A replan-resolved blocking divergence uses exactly `- Resolution: plan revision <positive integer> committed recovery slice-NN`; that revision and slice must be the committed supersession owner. Supersession points to a new divergence of the same kind. Lifecycle `RESUME` may correct documentary authority but never mutates execution records; `REPLAN` reconciles that corrected authority and owns the execution transition.

Records with `Severity: blocking` and `State: active` require revalidation before corrective action. They block completion or execution close unless the exact current optional finding is explicitly bypassed under the gate contract; divergences cannot be bypassed. Resolved and superseded records remain auditable history.

Every new finding's `Evidence identity` equals the `VERIFIED` evidence ID of its origin attempt. `implementation_defect` requires conclusion `VALIDATION_FINDING`; `code_regression` requires conclusion `CODE_REGRESSION` backed by equivalent replay anchored to persisted historical evidence. Evidence `INVALID` or stale cannot create or sustain a finding. v1's closed persisted lifecycle is only `VERIFIED/NONE/{NONE,VALIDATION_FINDING,CODE_REGRESSION}`, `INVALID/VALIDATION_SIDE_EFFECT/NONE`, `INVALID/SANDBOX_BOUNDARY_BLOCKED/NONE`, or `INVALID/INVALID_REPLAY/NONE`; `OBSERVED`, evidence `SUPERSEDED`, and `STALE_EVIDENCE` are not persistible because v1 has no harness producer or authorized transition for them. `VALIDATION_SIDE_EFFECT` requires an observed protected mutation or fingerprint effect. `SANDBOX_BOUNDARY_BLOCKED` identifies authenticated access denied before mutation with no protected delta and never makes the attempt harmless or authoritative.

## Prior Validation Overlap

`- none` is valid only when no changed or corrected path intersects an earlier terminal `PASS`/`ACCEPTED` base. In a v1 task, every such intersection is declared exactly once and only as:

```markdown
### overlap-NN

- Prior slice: slice-NN
- Paths: <canonical comma-space task-relative paths>
- Affected behavior: <non-placeholder behavior>
- Regressions: <non-placeholder checks or observations>
```

The declared paths equal the intersection exactly. Every file-backed path in a successful Effective Validation Base must also be a Changed Areas claim (and correction claims remain a subset of Changed Areas), so a new owner cannot bypass this derived intersection through an undeclared base entry. A later terminal slice without this declaration is rejected; this records a derived relationship and never rewrites the earlier base.

On a terminal `SUPERSEDED` slice, unresolved records remain preserved historical context but no longer block the replacement slice or execution close. Its required later `PASS`/`ACCEPTED` owner is the effective authority.

## Delegation blocker singleton

Fresh materialization persists only `- none` under `## Delegation Blocker`. A definitive transport/initialization failure after the bounded technical retry, one malformed started-runner result, or an authenticated harness pre-check infrastructure/source-isolation block before any verification command replaces that sentinel with exactly one singleton:

```markdown
- Operation: EXECUTE_SLICE|APPLY_FINDINGS|VALIDATE_SLICE
- Kind: initialization|malformed-output|infrastructure
- State: active
- After record: none|implementation-check-NN|findings-check-NN|attempt-NN
- Pending automatic round: 1/3|2/3|3/3
- HEAD: <commit or not_available; infrastructure only>
- Evidence provenance: <exact opaque resolver transport; infrastructure only>
- Causes:
  - <objective compact cause>
- Required action: <objective executable recovery>
```

`After record` is the latest valid record for the named operation when the blocker was persisted. `Kind: infrastructure` is valid only under `stnl-validation-evidence/v1`; it requires the exact harness `HEAD` and `Evidence provenance`, a single cause equal to the authenticated blocker code/message, `INVALID/INFRASTRUCTURE_BLOCKED/NONE`, an unchanged live pre-check snapshot, no isolated workspace, no subjects, no commands, and no replay. Initialization and malformed-output blockers cannot claim harness provenance. A provenance-less or internally inconsistent infrastructure claim is malformed. Only the same operation on the same slice may resume directly at delegation. A later valid operation record atomically changes the singleton to `State: resolved` and adds `- Resolution: <objective result naming that later record>`. `Resolution` is forbidden while active and mandatory while resolved. A resolved singleton remains historical and is projected as `historical-resolved`, never as the current effective blocker. The current `effectiveBlockers` projection comes from an active singleton or the latest evidence-bearing `BLOCKED` record. A new auxiliary or formal recovery blocker therefore remains visibly active even when an older singleton is resolved; valid resumed evidence clears the effective projection while preserving both histories. It is invalid to keep the singleton active after a later valid record or to mark it resolved without one.

For `EXECUTE_SLICE` and `APPLY_FINDINGS`, `Pending automatic round` is mandatory in v1 tasks and reserves the logical invocation that failed to start or failed during authenticated pre-check: `1/3` before any record, the same round as the latest `BLOCKED` record, otherwise the immediate successor of round 1 or 2 `TESTS_FAIL`. `VALIDATE_SLICE` uses no automatic round and omits this field. Recovery resumes the reserved round; transport, pre-check infrastructure failure, or authenticated boundary denial does not consume, advance, or reset it. No duplicate identifier, duplicate allocation, fourth round, or stale invalid-evidence authority is permitted.

## Auxiliary check evidence

Each record uses the next section-global identifier, `implementation-check-NN` or `findings-check-NN`, and includes:

- automatic round `1/3`, `2/3`, or `3/3` for the current manual operation;
- status `TESTS_PASS`, `TESTS_ACCEPTED`, `TESTS_FAIL`, `TESTS_NOT_APPLICABLE`, or `BLOCKED`;
- HEAD, tested scope, complete tested state hashes/removals, or exact `Tested state: none` plus an objective `Fileless reason`;
- canonical discovery sources and relevant read-only discovery actions;
- verification types considered and exact commands with numeric exits;
- exact opaque `Evidence provenance` transport returned by the validation resolver;
- non-applicability rationale and no-command confirmation when applicable;
- selected checks, rationale, coverage, failures, blockers, unexpected effects, and persistence summary;
- prior-round failure, correction, files, and updated in-slice rationale when applicable;
- for findings checks, finding cycle/IDs, findings verified, corrections covered, regressions, and unsupported active findings.

The exact mandatory fields are `Automatic check round`, `Status`, `HEAD`, `Tested scope`, `Tested state`, `Discovery sources`, `Discovery actions`, `Verification types considered`, `Commands`, `Selected checks`, `Selection rationale`, `Coverage`, `Failures`, `Blockers`, `Unexpected workspace effects`, and `Persistence summary`. Scalar summaries are compact opaque inline values with no nested list. In `TESTS_PASS` or `TESTS_ACCEPTED`, exact `none` is forbidden specifically for `Tested scope`, `Verification types considered`, `Selected checks`, and `Coverage`; it remains legitimate in fields such as zero blockers or unexpected effects. `Commands` and file-backed `Tested state` are the only structured nested fields in an auxiliary record. `Commands` contains exact backticked commands with numeric exits; only `TESTS_NOT_APPLICABLE` or `BLOCKED` may use exact scalar `none`. File-backed `Tested state` paths are normalized task-relative, unique, lexicographically ordered, and paired with lowercase SHA-256 or `REMOVED`. A fileless record instead uses exact `Tested state: none` and exactly one non-placeholder inline `Fileless reason`; the field is forbidden for file-backed state. Round 2 or 3 additionally requires non-placeholder `Prior-round failure`, `Correction applied`, `Updated scope`, and `In-slice rationale`; file-backed `Correction paths` is an exact comma-space-delimited normalized ordered set, while exact `none` is permitted only for the corresponding fileless correction. A findings check additionally requires `Findings cycle`, `Finding IDs`, `Findings verified`, `Corrections covered`, `Regressions`, and `Unsupported active findings`. `Finding IDs` is one non-empty lexicographically ordered set and is the canonical target set. `Findings verified` is exact `none` or a canonical subset of `Finding IDs`. `Unsupported active findings` is deterministically every active finding at the named cycle not present in `Findings verified`; verified and unsupported never overlap. Membership, declaration, ordering, and cycle checks remain strict. A trailing round 1 or 2 `TESTS_FAIL` is invalid unless an active blocking divergence explains why the authorized automatic correction cycle stopped, or a later formal attempt has taken ownership of the current verdict.

For `EXECUTE_SLICE`, every mandatory checklist item and related execution state is persisted in the same isolated task candidate before a terminal implementation record (`TESTS_PASS`, `TESTS_ACCEPTED`, `TESTS_NOT_APPLICABLE`, or round `3/3 TESTS_FAIL`) may be added. Candidate validation rejects terminal implementation evidence with an incomplete checklist. A pre-existing live inconsistency is not treated as generic corruption or routed through `REPLAN`: the runtime preserves its observed state but exposes exactly one mandatory target, `stnl-slice-executor / EXECUTE_SLICE / <affected slice>`, with the terminal record and round. That recovery may only make the approved execution/checklist record complete, preserves terminal evidence and formal history, is repeatable before publication, and publishes the complete task artifact once. After completion, normal validation or retry-exhaustion authority resumes. A complete `IMPLEMENTED_AWAITING_VALIDATION` task never reopens execution.

A round `3/3 TESTS_FAIL` persists normally and enters `IMPLEMENTATION_RETRY_EXHAUSTED` or `FINDINGS_RETRY_EXHAUSTED`. The executor cannot re-enter either operation until explicit `VALIDATE_SLICE` records the next formal verdict, except for the exact same-slice incomplete-implementation recovery above.

In a v1 task, `Evidence provenance` is mandatory in every new auxiliary record in addition to the exact fields above. Its subjects equal file-backed `Tested state`, and its recorded command displays/exits equal `Commands`; fileless evidence uses empty subjects and commands as permitted by status.

## Validation Attempts

Every successfully started formal validation that reaches an evidence-bearing check result appends the next `attempt-NN`. `attempt-01` is `initial`; later attempts are `revalidation`. Each records exact status `PASS|ACCEPTED|NEEDS_FIX|BLOCKED`, HEAD, verified scope, commands and exits, evidence, finding references, blockers, unexpected effects, and persistence summary. Transport, malformed-output, and authenticated pre-check infrastructure blockers remain outside attempts under their singleton contracts.

The exact mandatory attempt fields are `Type`, `Status`, `HEAD`, `Verified scope`, `Commands`, `Evidence`, `Finding references`, `Finding dispositions`, `Blockers`, `Unexpected workspace effects`, and `Persistence summary`. Scalar summaries stay inline and opaque. Commands have numeric exits and remain structurally scoped to `Commands`; only `BLOCKED` may use exact `none`. `Finding references` uses exact `none` or `finding-NN, finding-NN`. `Finding dispositions` uses exact `none` or `finding-NN=active|resolved|superseded, finding-NN=active|resolved|superseded`. Both use unique lexicographically ordered canonical IDs with identical identifier sets, and every attempt disposes every finding whose origin is at or before that attempt according to the deterministic timeline. A finding `Origin` names an existing `NEEDS_FIX` attempt. Resolution and supersession authority is strictly later than that origin. The first `PASS` or `ACCEPTED` attempt is terminal: no later `PASS`, `ACCEPTED`, `NEEDS_FIX`, `BLOCKED`, or other `attempt-NN` may exist. Prior `NEEDS_FIX` history and the final owning PASS/ACCEPTED remain valid.

In a v1 task, exact opaque resolver `Evidence provenance` transport is also mandatory in every new Validation Attempt. The deterministic `priorEvidenceId` links the immediately prior record in the same validation stream; an invalid observation remains auditable but cannot act as a verified baseline for its successor.

## Structured evidence provenance

New evidence carries exact protocol `{runner:"stnl-validation-runner/v10",harness:"stnl-validation-harness/v10",capability:"sha256:<canonical validation capability>"}` plus a harness receipt. The loaded runner obtains the capability from its already-loaded contract, while the resolver and harness verify the installed package manifest and local bytes; missing, stale, or same-version-but-different identity blocks before verification. Protocol and capability participate in execution, evidence, and replay identity. The resolver validates canonical harness stdout and emits one opaque `stnl-validation-result/v1` envelope; the owner transports it exactly and never parses, fills, reconstructs, copies into a new record, repairs, or recalculates provenance fields. Direct current JSON, raw exit/stdout, a test count, textual PASS/BLOCKED, provenance without a matching receipt, or historical evidence cannot publish a check, attempt, finding, Effective Validation Base, TASK, or lifecycle transition.

Missing, unknown, or mixed runner/harness protocol produces `VALIDATION_PROTOCOL_INCOMPATIBLE` at `protocol-preflight`; a missing or stale loaded capability produces `VALIDATION_CAPABILITY_IDENTITY_MISMATCH`, and installed package byte/manifest drift produces `VALIDATION_PACKAGE_IDENTITY_MISMATCH`, both at `identity-preflight`. Each is `INVALID/INFRASTRUCTURE_BLOCKED/NONE`, with no finding/regression/VERIFIED and no command. Missing `executionEnvironment` in a new request produces `EXECUTION_ENVIRONMENT_REQUIRED` at `environment-preflight` before commands and never defaults to host.

Inside the opaque transport, `Evidence provenance` is one deterministic JSON object with version, evidence ID, receipt, exact protocol/capability, prior evidence ID, lifecycle state, classification, proposed conclusion, operation, slice, round, workspace, inputs, subjects, commands, replay, and nullable generated-write recovery. Authenticated infrastructure results additionally carry an exact blocker object (`kind`, `stage`, stable `code`, `message`, and optional project-relative `target`). The workspace records isolated-copy identity, cwd/execution root, before/after fingerprints for live execution, live workspace and isolated execution, cleanup, ordered actual side effects, and ordered authenticated `boundaryViolations`. A changed live-workspace fingerprint additionally requires a deterministic delta with exact added/modified/removed counts, up to 64 ordered project-relative identities, truncation state, and a fingerprint of the complete change set; an unchanged fingerprint requires no delta. A pre-check blocker normally has `cleanup: not-required`; if a known cleanup fails it instead has `cleanup: failed` plus every deterministic cleanup residual in `sideEffects`, without replacing the root blocker. An authenticated Docker failure after admission records `stage: environment-execution` against the isolated copy and the attempted Docker command, and may likewise coexist with cleanup residuals. Inputs record current requirements authority, plan revision, Git `HEAD` or exact `not_available`, source, subject manifest, baseline, changed scope, and execution fingerprints. Subjects preserve each normalized task-relative file identity with SHA-256 or `REMOVED`; directory-level collapse, basename aliases, duplicates, symlinks and hardlinks are invalid. Commands preserve display, argv, cwd, ordered bounded directory `writePaths`, ordered exact new-generated-output `writeFiles`, environment/executable fingerprints, nullable admitted/post-run external-toolchain fingerprints, timeout, exit, and stdout/stderr fingerprints.

Each boundary diagnostic has exact stable fields `{kind, operation, process, command, commandExecutable, requestedPath, resolvedPath, trustedRoot, boundary, rule, deniedBeforeMutation, liveWorkspaceChanged}`. Paths use stable trusted-root representations such as `$PROJECT`, `$VALIDATION_RUNTIME`, `$AUTHENTICATED_TOOLCHAIN`, `$LIVE_PROJECT`, `$HOME`, `$SYSTEM_TEMP`, `$SYSTEM`, or `$ABSOLUTE`; generated timestamp/nonce segments are redacted. Process IDs, timestamps, random temp directory names, nonces, arbitrary environment values, and secrets are forbidden. The command index and fingerprint identify the responsible command deterministically. A diagnostic reports the authenticated backend operation and rule, not an inference from stderr. Only a write denial authenticated as denied-before-mutation inside the isolated workspace can seed generated-output recovery. `sideEffects` contains only observed protected mutations/fingerprint/cleanup/toolchain effects; a denied-before-mutation attempt with unchanged live state is represented in `boundaryViolations`, not mislabeled as an actual side effect.

The harness first derives and verifies the legal operation, slice, round and immediate prior evidence ID from current lifecycle state, then executes verification only in an operating-system sandbox over an isolated copy. Live and copied execution state are protected; private session HOME/TMP, explicit non-overlapping project directory `writePaths`, and exact project `writeFiles` are the only mutable locations. An exact `writeFiles` target must be absent from the initial copied-source snapshot and have an existing real source parent; the harness never creates a placeholder, so the command observes the target as absent and may create it exclusively or leave it absent. Authority is per-command: a later command may rewrite a generated file only when it declares that same exact file. macOS grants literal exact-file creation without granting parent or sibling writes. Linux `bwrap` v1 returns deterministic authenticated `INFRASTRUCTURE_BLOCKED` pre-check provenance for nonempty `writeFiles`, because its bind model cannot expose a nonexistent exact file without pre-creation or writable-parent sibling authority. An external launcher is trusted only when it resolves from an inherited canonical PATH `bin`, its target has a canonical package boundary, and its shebang interpreter is system-owned or inside that same concrete installation. The harness executes a sparse authenticated snapshot containing only the launcher, package dependency tree, and required same-installation interpreter; macOS grants that snapshot read-only access and Linux exposes it with an explicit read-only bind while hiding the live home. Caller-selected external roots, escaping/broken/ambiguous links, post-admission mutation, broad HOME/NVM/temp authority, and toolchain writes fail closed. The admitted toolchain fingerprint participates in command, execution, evidence, and replay identity. Before the first verification command, a supported sandbox/backend failure or source-admission/isolation rejection produces deterministic `INVALID/INFRASTRUCTURE_BLOCKED/NONE` provenance and a `BLOCKED` result without claiming subjects, commands, or an isolated workspace. An authenticated Docker create, start, wait, logs, required kill, or other execution operation failure produces the same lifecycle result with `kind: execution-environment`, `stage: environment-execution`, the attempted command, and isolated-workspace provenance; it never becomes a validation finding or regression. Cleanup failure, authenticated boundary denial, any protected side effect, stale source/manifest/scope/authority, or invalid reproduction makes evidence `INVALID` and permits only `BLOCKED`. When a trusted boundary diagnostic identifies a denied-before-mutation write to a path initially absent inside the isolated project, the harness may retry exactly once in the same logical round or attempt. It derives either the exact future `writeFile` or the first absent necessary `writePath`, rejects `.`, parent/project escape, execution state, protected subjects, pre-existing targets, symlinks, hardlinks, special files, external toolchains, HOME, runtime roots and overlapping sibling authority, and records the origin evidence ID and exact authorizations in final provenance. stderr alone never authorizes recovery, and invalid evidence itself authorizes no product correction. A replay origin must be a prior persisted `VERIFIED` evidence record. `VERIFIED` evidence is still not persistence authority.

Physical execution authority is explicit per command. `host` preserves authenticated inherited-PATH toolchains. `docker-compose` requires one canonical Compose file, one validated service identifier, its declared local image reference, and separate project instruction sources; a Dockerfile, Compose file, Docker availability, or host lookup failure alone never selects it. The harness authenticates the locally available image declared for the service and confirms materialized container labels when present and runs logical argv in a new hardened container over only the isolated project copy, never the live Compose container. The copy is read-only except for declared `writePaths`; network, Docker socket, capabilities, extra privileges, external host mounts, and exact future-file writes are denied. Missing or ambiguous Docker environment state is pre-check `INVALID/INFRASTRUCTURE_BLOCKED/NONE`, with `kind: execution-environment` and `stage: environment-preflight`; authenticated failure after admission uses `stage: environment-execution` with the same lifecycle and never falls back to host or becomes a finding. The selected environment, project authority file identities, Compose configuration identity, and container image identity participate in command, execution, evidence, and replay fingerprints. A direct host .NET installation remains independently admissible only when the executable and bounded sibling `sdk/` establish its package boundary.

Docker commands may optionally declare exact `cacheVolumes` entries `{source,target}`. Each source must be a locally managed named volume declared both on the selected service and in the same Compose top-level volumes mapping under an explicit project `name`; the physical volume name, local driver/scope, and Compose labels must agree. The harness copies it once through a hardened disposable helper into a temporary snapshot, rejects symlinks, hardlinks, and special filesystem entries, mounts only the snapshot read-only outside `/workspace`, and includes volume metadata plus snapshot content identity in execution evidence and replay. It never mounts the live named volume into a validation command, enables network, accepts an external path, or projects unrelated Compose properties.

Replay additionally records original/current execution fingerprints, equivalence and ordered material mismatches. The original evidence ID must resolve to prior persisted evidence of the same slice. Equivalence covers operation, slice, round, cwd, execution root, authority/revision, the source snapshot excluding execution state, file manifest, baseline, changed scope, physical execution environment, argv/write paths/write files/environment/executable, and execution fingerprint. A mismatch is `INVALID_REPLAY`, skips execution, has conclusion `NONE`, and cannot support `code_regression`.

## Effective Validation Base

At most one current base exists and it originates from the current `PASS` or `ACCEPTED` attempt (use the same exact Result):

```markdown
- Origin attempt: attempt-NN
- Attempt type: initial|revalidation
- HEAD: <commit or not_available>
- Result: PASS
- Files:
  - `<relative/path>` | sha256:<64 lowercase hexadecimal characters>
  - `<removed/relative/path>` | REMOVED
- Authoritative commands:
  - `<exact command>` | exit:<integer>
- Evidence summary: <compact evidence>
```

A valid fileless PASS/ACCEPTED uses the same record with exact `- Files: none`, followed immediately by `- Fileless reason: <objective non-placeholder reason>`. It keeps authoritative commands and the owning attempt's exact evidence summary. A file-backed base forbids `Fileless reason`; a fileless base forbids path/hash tuples and requires `Changed Areas` to be exact `- none`.

For v1, the base `Files` equals the owning attempt's provenance subjects exactly; its authoritative commands/exits and evidence summary remain identical to that attempt. Candidate validation rechecks current bytes before a newly terminal PASS/ACCEPTED is publishable, and CLOSE repeats ownership verification against every terminal base.

## Superseded slice terminal record

Only append-only approved-replan materialization writes this terminal result for an open slice:

```markdown
## Final Result

- SUPERSEDED
- Superseded by: slice-NN
- Plan revision: <positive integer>
```

The matching global row is `[x]` with Validation and Result `SUPERSEDED`. This preserves history and satisfies serial progress without claiming successful validation. A historical `PASS` or `ACCEPTED` is never changed to `SUPERSEDED`.

## Quality gate observations, revalidation and acceptance

The independent runner evaluates slice obligations and relevant regressions, not global repository perfection. A failed command is raw evidence, not an automatic slice verdict. For each failure, determine scope and causal relevance separately. `out_of_scope + independent` is `non_blocking`; record the external debt without adding correction paths. A demonstrated slice-caused external regression blocks. Try an authorized in-scope cause/adapter correction before proposing authority expansion. Unknown causality requires bounded investigation and, if unresolved, temporary `BLOCKED`, never automatic `REPLAN`. Merely finding an external path or lacking a baseline does not prove causality. Independence needs evidence (baseline comparison, unchanged diagnostics plus dependency/diff analysis, or equivalent); do not infer it only from the path.

Use optional inline `- Gate assessments: <JSON array>` inside the existing auxiliary check or Validation Attempt. It is required for any nonzero exit claimed non-blocking, bypass, revalidation-based divergence resolution, or gate-driven REPLAN. No new artifact or section is created. Legacy records without assessments retain their strict exit-code rules and remain readable; reobserve their causes before deciding recovery. The exact nonempty array items have these keys, without extras:

- `id`: stable `gate-NN`, unique within the record. Reuse an ID only for the same gate identity.
- `command`: exact recorded command, or JSON `null` for an inspected condition without a command. Every non-null command must have a raw numeric exit in `Commands`.
- `kind`: `quality`, `requirement`, or `structural`. Mandatory acceptance criteria, required evidence/coverage and required integration are `requirement`; corrupt lifecycle, missing artifacts, incomplete tasks, dependency and authority integrity are `structural`. Never relabel either to enable acceptance. Structural/mandatory obligations remain protected through gate revalidation lineage: a still-present original obligation cannot be demoted to non_blocking or bypassed by relabeling a successor.
- `scope`: `in_scope` or `out_of_scope`.
- `causality`: `independent`, `caused_by_slice`, `required_by_slice`, or `unknown`.
- `state`: `present` or `absent`, observed now, including uncommitted working-tree corrections by any actor.
- `problem`, `evidence`, `correctionEvidence`: objective non-placeholder text. Evidence accounts for every diagnostic in the gate, current observations, baseline/diff/dependency analysis and requirement coverage. `correctionEvidence` states the valid in-scope correction or explains why every viable correction requires authority change. Unknown investigations name the missing causal evidence.
- `diagnostic`: `sha256:<64 lowercase hex>`, the digest of normalized diagnostic identity/content (rule/behavior, affected paths/contracts and material failure details). Exclude timestamps and unrelated output; do not reuse a digest for materially different failures.
- `correction`: `in_scope`, `authority_change`, or `unknown`.
- `revalidates`: JSON `null`, a prior `attempt-NN/gate-NN`, `implementation-check-NN/gate-NN`, `findings-check-NN/gate-NN`, or an existing `finding-NN` / `divergence-NN`. Prior gates/findings must already exist. Reobserve all still-applicable blockers and bypasses; never omit one to obtain success.
- `snapshot`: an array of exact `{ "path": "<task-relative path>", "expected": "sha256:<64hex>|REMOVED" }` objects for the relevant causal/observed files, unique and sorted. An environment-only observation may use `[]` with concrete current executable evidence. REPLAN requires a nonempty causal snapshot. Candidate validation checks newly published observations against actual working-tree bytes; changed HEAD alone neither resolves nor perpetuates a blocker.
- `bypass`: JSON `null` or exact `{ "target": "sha256:<64hex>", "operator": "<identity>", "reason": "<accepted risk>", "authorization": "<explicit operator request/reference>" }`.

`evaluateQualityGate` in the bundled runtime derives decisions: absent -> `resolved`; structural -> `blocking`; independent external quality issue -> `non_blocking`; unknown causality -> `investigate`; a current caused/required issue whose correction demonstrably changes authority -> `replan`; otherwise -> `blocking`. REPLAN requires all five facts: real relevant issue, current observation, slice causality/obligation, necessary authority change, and no valid in-scope fix. Runtime parses and checks supplied evidence; the independent runner owns its technical truth and completeness. A failed command must account for all failures, including mixed independent and relevant failures. Zero-exit focused checks must still prove every mandatory slice requirement; an unrelated success is insufficient.

For explicit acceptance, first revalidate. If the condition disappeared, record `resolved`; if independent and external, record `non_blocking` (the acknowledgement), without requiring bypass. Only a still-valid optional `quality` blocker with known causality and an in-scope remedy is bypassable. Structural gates, required obligations, unknown causality and authority changes cannot be bypassed. `qualityGateIdentity(gate, {fingerprint, revision, slice})` computes the exact target from the authority, slice, gate, command, kind, scope, causal classification, diagnostic digest and correction boundary. Free-text problem, evidence, correctionEvidence, timestamps and observation snapshots do not enter the identity; material diagnostic changes do. The bypass must match that target and a prior concrete blocking observation, even when retained only as history after recovery. Historical metadata must match its previously recorded authorization and never makes the current result ACCEPTED. If any material identity field changes, keep the old bypass only in its original record and use null for the new observation unless newly authorized. New/materially different diagnostics, gates, authority or slices require new explicit authorization. Persist operator, reason and exact authorization in the next observation; never infer consent from a generic request to finish. Authorization provenance is checked by the model-owned writer against the operator request, as with existing mutation ownership; a string is not cryptographic proof of consent.

`PASS` / `TESTS_PASS` permits nonzero commands only when every failure is independently established as non-blocking. Preserve the actual exits in both attempt and base; never rewrite failure to zero or silently drop a failed command. A still-bypassed gate requires `ACCEPTED` / `TESTS_ACCEPTED`, never `PASS`. `ACCEPTED` has the same mandatory checklist, requirements, manifest, hash, overlap, dependency, authority and publication checks as PASS and a current valid bypass. Its attempt, Effective Validation Base `Result`, Final Result and global Validation/Result are all exactly `ACCEPTED`. It is terminal, immutable and eligible for serial continuation, with explicitly accepted quality debt. A base still contains exactly its owning attempt's commands and evidence. CLOSE verifies both PASS and ACCEPTED ownership and reports retained acceptances distinctly; it cannot turn ACCEPTED into PASS. Auxiliary acceptance never completes a slice or replaces formal validation.

On resume, the preflight is a read-only structural gate and exposes `REVALIDATION_REQUIRED`; it does not execute stored shell strings. The owning runner freshly checks the actual condition, even at the same HEAD and even when no relevant bytes changed. A prior BLOCKED is not returned as a fresh verdict. Append the next check/attempt and preserve earlier observations. A prior bypass is reevaluated against current diagnostics; it carries forward only for the exact still-valid gate. Delegation recovery retries the logical invocation, resolving the singleton with the next valid record. Auxiliary BLOCKED resumes its owning operation at the runner, without redoing completed work. Findings may go directly to VALIDATE_SLICE to inspect manual fixes; APPLY_FINDINGS first inspects current state and need not manufacture another code change.

An active divergence may be rechecked through the runtime's `blocker-revalidation` target before lifecycle/replanning mutation. Revalidation cannot alter requirements or plans. If no longer true, its owning executor or quality manager may change only its state to `resolved` with `Resolution: <check-or-attempt-NN> revalidated: <objective reason>` and a matching `revalidates` assessment deciding `resolved` or `non_blocking`; preserve original problem/evidence/authority fields. Divergence `Kind` is structured and immutable: omitted Kind in legacy records means `authority`. Only `observational` with `Required authority operation: none` permits `non_blocking`. Authority/lifecycle (`RESUME` or `REPLAN`), `structural` and `required` divergences can resolve by revalidation only when the condition is objectively `absent`; while present they retain the original mandatory handoff and cannot become optional debt. These restrictions follow the gate revalidation lineage, not just direct divergence references. No divergence permits bypass, including historical metadata. A still-true authority divergence retains its authority handoff. Existing committed-replan divergence resolution remains valid. After an interrupted early TESTS_FAIL plus divergence, a fresh round 1 is allowed only with this explicit divergence revalidation. Required checklist items must be complete before formal validation.

Formal findings stay under quality-manager ownership. A BLOCKED attempt may now resolve a corrected prior finding only with its own explicit `resolved`/`non_blocking` gate evidence; unrelated blockers do not keep corrected findings active. A bypassed finding stays historically `active`, with the exact current gate acceptance removing only its effective blocking effect; it is never marked corrected. A PASS must resolve/supersede all active blocking findings; ACCEPTED may retain only explicitly bypassed optional findings. A future attempt must reassess every still-active finding and acceptance.
