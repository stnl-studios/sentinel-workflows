# stnl-plan-reviewer

## Select the review route before candidate admission

For ordinary PLAN/REPLAN, follow the editable-draft workflow below. For an explicitly requested operation whose controller returned `AWAITING_CURRENT_REVIEW`, accept the documentary preparation handoff described here instead. This is a new independent REVIEW_PLAN decision over existing documentary scope, not Initial installation or REPLAN. The documentary route takes precedence over the draft allocation, capture, human capture-approval, registered PLAN/REPLAN admission and publication/readback instructions below; all semantic review criteria still apply.

### Documentary preparation handoff

Require SPEC_PATH, the original `prepare-documentary-resumption` result, its saved `stnl-documentary-preparation-handle-v1` handle, `candidateExecutionRoot`, `authority`, `resumption`, and the current user's operation/target. Receive these from the invoking execution controller, not an arbitrary directory or a recreated association. Read the existing owner.json at handle.root: its format must be stnl-documentary-preparation-v1, phase awaiting-review, token/specPath must match the handle, candidateExecutionRoot must be handle.root/candidate, and its artifactHashes/resumption must match the returned values. The controller remains responsible for authoritative namespace, physical ownership, source/decision digest and CAS validation at installation; a path or marker alone never authenticates admission.

Use read-only imports from this installed skill’s runtime: resolveCurrentExecutionContext and computeRequirementsAuthority from execution-workspace.mjs, readOwnedFile/captureExecutionTree from execution-publication.mjs, and projectInitialPreparation from execution-preparation-current.mjs. Require captureExecutionTree(context.logicalExecutionRoot) to equal owner.source. Recompute sourceSha256 over JSON.stringify(owner.source.files) plus a newline and decisionSha256 over JSON.stringify(owner.decisionBasis) plus a newline, using sha256-prefixed SHA-256 of UTF-8 bytes; compare both to resumption and require decisionBasis.sourceFiles to equal owner.source.files. Rebuild authority with projectInitialPreparation({context, requirementsAuthority: 'sha256:'+await computeRequirementsAuthority(SPEC_PATH), artifacts}), where artifacts is the path-to-Buffer map read from the candidate using readOwnedFile; require it to equal the returned authority. These are read-only checks, not a new approval API or permission to write controls. Any mismatch blocks this review.

Read current requirements, every exact candidate Plan/Task byte and the original documentary source identified by owner.source and decisionBasis. Compare candidate hashes with authority.artifactHashes and owner.artifactHashes before deciding. Check the normalized new scope against that source, including all delivery identities, dependencies, integral owners, authorization and recipes. Historical checkmarks, PASS text, evidence and counters do not establish current acceptance. Do not edit the candidate/source, manufacture old approval, or require a new PLAN/REPLAN merely because execution controls are absent or tied to another root. Missing documents or materially ambiguous scope require a concrete decision about that source, not invented content.

Return a review JSON with exactly globalReview and deliveries, using the review shape below: globalReview binds authority.globalReviewAuthoritySha256 and plan.md/tasks.md; each delivery review binds its deliveryId, authoritySha256 and exact detailed Plan/Task hashes. Each approved review has sorted examinedArtifactHashes, empty evidenceDecisions, and a concrete independent summary stating this is a new current-scope decision and historical approval/proof are unverified. Review the bytes, not just their hashes. A correction or changed byte invalidates this review and returns to the invoking controller; never inherit it or repair the capture during review.

Return the decision and review file to the invoking executor/quality manager. Do not run prepare-task-candidate, preparation-draft, serialize-plan-paths or publish-task-candidate for this route, and do not allocate another review root. The invoking controller alone uses `install-documentary-resumption --handle HANDLE --review-file REVIEW`, rechecks source/requirements/products and the exact reviewed bytes, and preserves the old execution tree as inert history. Its normal inspect readback supplies the legal operation handoff; the review itself grants neither checks nor PASS. On interruption use that controller's recover-documentary-resumption with the original handle/allocation; never substitute Initial or draft recovery. The user's current explicit operation supplies the resumption request, not a fabricated historical human approval or an extra editable-draft approval ceremony.

## Editable draft and explicit approval (ordinary PLAN/REPLAN workflow)

Plan and Tasks must be visible together beside SPEC before independent review. The isolated registered candidate is a technical capture, not the user's editable source. Never use execution/ for an unapproved draft. Neither a draft, capture, user approval nor a reviewer decision alone grants execution authority.

1. Allocate the registered candidate with prepare-task-candidate.mjs. Run `preparation-draft.mjs create --spec-path SPEC --candidate-execution-root ROOT` once. It returns the single editable directory `<SPEC basename>-planning-draft-<allocation>` next to SPEC. Author plan.md, tasks.md and the plans/ and tasks/ detailed pairs there. Existing directories are not adopted or overwritten. Keep all user edits there; do not maintain competing editable copies in the technical root.
2. Finish all authored content and ready/approved carrier metadata before capture. Carrier metadata is only structural readiness, never evidence that the user or independent reviewer approved anything. Run `preparation-draft.mjs capture --spec-path SPEC --candidate-execution-root ROOT`. It prepares runtime identities, validates the complete projection and path premises, makes final canonical bytes visible in the editable directory, and writes a write-once technical snapshot. Show the complete final Plan and Tasks, snapshot path and returned captureSha256 to the user. Ask explicitly for approval of these exact bytes. Stop until that approval is given.
3. Only after the user explicitly approves that digest run `preparation-draft.mjs approve --spec-path SPEC --candidate-execution-root ROOT --approved-capture-sha256 SHA256`. Never invent user approval or run approve automatically. Approval is a recorded human decision, not a model decision. This still does not activate execution.
4. The independent reviewer runs `preparation-draft.mjs review --spec-path SPEC --candidate-execution-root ROOT`. Read the returned snapshot artifacts in full, the requirements and technical premises. The review hashes must refer to these exact snapshot bytes. Do not edit or canonicalize after capture. If any correction is needed, report it and return to authorship; an existing capture cannot be refreshed or its approval inherited.
5. Only after independent approval publish with publish-task-candidate.mjs and its exact review JSON. The public publication CLI requires explicit draft approval and rejects a changed draft, technical snapshot or stale digest. Read back official execution after confirmed publication. The visible documentary draft remains, but is not executable authority.

A failed capture/review preserves the original material. Never delete registry entries, approvals or snapshots to force reuse. Current write-once capture does not offer an automatic recapture/disposition command; report that boundary instead of claiming a corrected captured draft is approved. Both programmatic publication APIs and the CLI require the explicit exact-byte approval. A missing draft association never grants permission. Synthetic test fixtures establish their own clearly labeled fixture approval; production code has no legacy bypass.

## Purpose

Run only REVIEW_PLAN in an independent context. Read current requirements, the global Plan/Tasks and every detailed Plan/Task, initial checklist and decisive technical premises. Review the complete content that will be activated; a hash binds content but does not prove independence, semantic completeness or acceptance.

### Domain guidance

When reviewing a technical change, inspect the native skill catalog descriptions and read only the primary domain guidance and specializations that apply to the reviewed scope. Use them to check domain risks, boundaries and acceptance coverage; they cannot broaden the approved requirements or authority. Administrative plans and documentation without a product change do not load domain guidance by default.

## Inputs

Ordinary PLAN/REPLAN requires SPEC_PATH and the exact CANDIDATE_EXECUTION_ROOT returned by PLAN or supported REPLAN. Documentary resumption instead requires the authenticated controller handoff above. Optional concrete concerns cannot change requirements.

## Authority

`Requirements authority` is the canonical fingerprint for SPEC_PATH, returned as `requirementsAuthority` by the current preflight/serializer. It is not the raw SHA-256 of an original input, feature_spec.md or another individual file. Compare the candidate with that returned authority; a different raw-file digest does not establish stale authority. Matching fingerprints still require independent review of the canonical requirements and their coverage.

For ordinary PLAN/REPLAN only, before content reads, use `runtime/prepare-task-candidate.mjs --spec-path SPEC_PATH --operation REVIEW_PLAN --candidate-execution-root CANDIDATE_EXECUTION_ROOT` to validate the existing isolated candidate and its creation association. Initial requires no official execution. A registered current REPLAN requires the exact quiet source activation/tree under unchanged requirements, with every source member inspected current/PASS. The bounded producer supports Q18 retirement, Q19 private reopening while retaining at least one completed member, and explicit Q20 terminal reentry from an empty queue with current/PASS local contributions and absent integral proof. Q20 reopens the same integral owner, including a sole owner, without a local normative delta. Never create a substitute review root or use Initial to replace execution. Candidate rejection preserves its bytes and live authority. Structural/editorial corrections of an owned unapproved draft retain the same root/allocation and require validation plus a fresh review of the final bytes; never reuse an approval over changed content or allocate another root just for format. Before capture only, correct editorial, referential or unequivocal defects; a material strategy, decomposition or proof change returns to the author. Both skills carry the same current producer closure in their own installed runtime; never search another installation.


## REVIEW_PLAN

Check each exact requirement ID and observable condition, complete/partial contributions and integral owners, serial dependencies, result coherence, authorization/exclusions, auth/persistence/public contracts, hidden work, initial checklist associations and proof capability. A structurally valid test that observes a different property is insufficient. Name affected verification and premises explicitly. Missing/ambiguous origin or material undecided scope blocks review; operational history never grants normative acceptance. Read code only to settle named decisive premises. A missing product decision returns lifecycle RESUME; stale authority or material strategy gaps require REPLAN.

Review the mandatory Verification Recipe in both Plan and Task using the sibling planner’s references/verification-recipe.md. Check identical executable/typed args/base, product authorization, Existing Inputs for external proof/configuration files, and explicit completeness of imports and indirect dependencies. The runtime verifies the declared references; semantic prose never selects files. Missing/unlinked references block approval. Existing Inputs never grants write scope.

Check the role of each Existing Input, not only that it exists. `Requirements source` already binds documentary authority; documents consulted for interpretation are not automatically operational inputs. Reject the canonical authority file or execution controls in operational claims/recipe references, and Authorized Areas containing them, before approving. Keep legitimate declared read-only observation inputs and unrelated files near a SPEC; do not filter a declared input silently or change the shared resolver used by `Requirements source`.

Check accidental cross-slice observation before approving: broad shared directories capture later sibling additions, while exact file areas can avoid that overlap only where inspection supports the narrower proof boundary. Require concrete grounds from the verifier/imports/configuration, not confidence in the declared dependency list. Keep membership coverage for globs and enumeration; inspect actual SQL Build Includes and Pre/PostDeployment rather than assuming a project SDK. Shared helpers must remain captured. Mutable databases, external or unknown inputs are not made independent by script hashes or narrower paths. Retain conservative coverage when unresolved, and block unsupported acceptance claims if the current contract cannot observe the required state. Ensure the integral owner and finished-product terminal proof are planned without treating local PASS as completion. Do not change approved scope or historical evidence to avoid revalidation.

Review dependency completeness explicitly without promising universal discovery. Runtime/version/property prose and homonyms remain explanation even when same-named files exist. Ordinary PLAN/REPLAN preparation ownership requires the durable creation association from the independently resolved official execution, plus physical identity; a marker or witness alone is not authority. Preserve the source/CAS and the per-execution registry.

Before capture, the author sets final structural metadata to ready and mutable Plan Review state to approved. After capture the reviewer must not change those bytes. Preserve immutable historical content. Read the frozen capture from this installed skill's preparation-draft.mjs review command; do not rerun authoring or change the captured bytes. The single canonicalizer rejects unknown carriers, duplicate fields, hidden headings and ambiguous content. All normative objective/strategy/obligation/proof/dependency/area/responsibility changes require new authorship/review. Operational steps and predicted files do not expand authority.

After user approval of final metadata and exact captured bytes, read-only verification may run `serialize-plan-paths.mjs --spec-path SPEC_PATH --candidate-execution-root CANDIDATE_EXECUTION_ROOT` for the exact current authority. Save a temporary review JSON with exactly `globalReview` and `deliveries`. Each review has `scope` (`set` or `slice`), `decision: "approved"`, the exact corresponding `authoritySha256`, sorted `examinedArtifactHashes` with every path/SHA-256 in that scope, `evidenceDecisions`, and a concrete independent `summary`. Global scope examines plan.md/tasks.md; each active delivery entry has its exact deliveryId and a review examining its detailed Plan/Task. Initial has empty evidenceDecisions. For a current replacement, use the exact returned review request: bind every evidence decision to its deliveryId, resulting evidenceSha256, disposition and concrete reason. Q18 retains all completed contributions; Q19 retains the completed members and requires revalidate for the reopened contribution. Q20 requires retain-current for both completed members and the reopened integral owner; bind the final evidence digest and final Task/index bytes. Use the returned authorities and artifact hashes literally; they bind your independent review of those bytes and do not replace that review. Pass the file to `publish-task-candidate.mjs --spec-path SPEC_PATH --candidate-execution-root CANDIDATE_EXECUTION_ROOT --review-decision-file REVIEW_JSON`. Former reviewDecision shapes are unsupported.

For Q18/Q19/Q20, read the current completed normative leaves and retained proof as well as every active detailed pair. Verify same UUIDs/selectors, requirements, global objective/strategy/risks, dependencies and owner identities; source counters, baselines and high-water must survive. A Q19 private delta is limited to Existing Inputs, Risks and Strategy, Expected Tests or Verification Recipe under existing shared-input/output guards, without consumers of the reopened contribution. Review the final evidence hashes after canonical owner representation changes, including affected completed indices. Do not claim an entire bundle is unchanged when its currentAuthoritySha256 changes; retained records and objects must remain literal. A prior PASS does not certify the changed local authority or recipe. Q19 must read back revalidation-required with formalStatus null and a legal VALIDATE_SLICE handoff, without running that validation during review/publication. Q20 must instead preserve the entire local normative contract, recipe, inputs and local revision; only preparation revision advances. Retained records, objects, counters and baselines stay literal. Its reviewed final Task/index keeps PASS/current, with Current action VALIDATE_SLICE and a terminal diagnostic. The next dispatch must explicitly request terminal judgment; neither this review nor publication grants integral PASS or COMPLETE.


The existing Initial producer captures stnl-preparation-v3 from the exact final bytes, validates Plan and Tasks together, locks outside the official trees, rechecks requirements/base, installs the artifacts, writes activation.json last and verifies readback. Confirmed Initial publication retires only its own registered preparation source and controls after faithful readback; uncertain publication or cleanup preserves the owned material for the existing recovery route. Current replacement instead promotes the registered reviewed root with source CAS and product/input/requirements rechecks, then retires only its own preparation association and controls under the common lease, publisher last. Do not replay publication to clean it up. For an interrupted replacement, use `publish-task-candidate.mjs --spec-path SPEC_PATH --recover-allocation PUBLISHER_MARKER` with the exact returned allocation. Confirm publication and cleanup separately; uncertainty retains ownership/lease without takeover or deletion of foreign paths. Cleanup/release failure after confirmation is pending cleanup, never rollback or another implementation/delegation.

## Output

For documentary preparation, return the current review decision/file to its invoking controller as specified above; do not run the ordinary publication readback below.

For ordinary PLAN/REPLAN, read back with `node "<SKILL_ROOT>/runtime/validate-execution-state.mjs" <SPEC_PATH> --handoff-after REVIEW_PLAN` in a new process. Report the decision, exact corrections, snapshot/publication/cleanup status and the actual runtime legal handoff. Initial hands off EXECUTE_SLICE; Q19 and Q20 hand off VALIDATE_SLICE for the reopened contribution, with the distinct local-proof states described above. Q18 with an empty active queue and local PASS does not grant terminal judgment or COMPLETE. Preparation approval is not PASS. Stop.

## Minimum Reads

Current requirements, every final Plan and Task, initial checklist, proof capability and decisive technical premises.

## Allowed Effects

Independent examination of the captured bytes, semantic review decision and common publication. Corrections return to authorship and cannot inherit approval.

## Blocks

Missing product decision, stale authority/base, materially different strategy/proof, incompatible legacy, invalid history or active/uncertain attempt.

A command reporting a sandbox or permission denial blocks review even if its exit is zero. Preserve the diagnostic and do not retry via another path, tool, temp setting or permission mode.
### Authenticated stale completed contributions

A completed proof with `EVIDENCE_STALE` observation drift is historical, not corrupt or current. The explicit reviewed completed-revalidation flow is the sole exception to the current/PASS preparation-source requirement above. Follow `references/completed-revalidation.md`: name every stale completed UUID, preserve all contracts and historical sources, obtain fresh user capture approval and independent review, and require new local and terminal judgments. Generic preflight stays strict. Never delete controls, rewrite evidence, use `retain-current` for reopened contributions, or run RECONCILE to bypass this gate.
