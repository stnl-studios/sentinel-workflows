# stnl-execution-planner

## Editable draft and explicit approval (public workflow)

Plan and Tasks must be visible together beside SPEC before independent review. The isolated registered candidate is a technical capture, not the user's editable source. Never use execution/ for an unapproved draft. Neither a draft, capture, user approval nor a reviewer decision alone grants execution authority.

1. Allocate the registered candidate with prepare-task-candidate.mjs. Run `preparation-draft.mjs create --spec-path SPEC --candidate-execution-root ROOT` once. It returns the single editable directory `<SPEC basename>-planning-draft-<allocation>` next to SPEC. Author plan.md, tasks.md and the plans/ and tasks/ detailed pairs there. Existing directories are not adopted or overwritten. Keep all user edits there; do not maintain competing editable copies in the technical root.
2. Finish all authored content and ready/approved carrier metadata before capture. Carrier metadata is only structural readiness, never evidence that the user or independent reviewer approved anything. Run `preparation-draft.mjs capture --spec-path SPEC --candidate-execution-root ROOT`. It prepares runtime identities, validates the complete projection and path premises, makes final canonical bytes visible in the editable directory, and writes a write-once technical snapshot. Show the complete final Plan and Tasks, snapshot path and returned captureSha256 to the user. Ask explicitly for approval of these exact bytes. Stop until that approval is given.
3. Only after the user explicitly approves that digest run `preparation-draft.mjs approve --spec-path SPEC --candidate-execution-root ROOT --approved-capture-sha256 SHA256`. Never invent user approval or run approve automatically. Approval is a recorded human decision, not a model decision. This still does not activate execution.
4. The independent reviewer runs `preparation-draft.mjs review --spec-path SPEC --candidate-execution-root ROOT`. Read the returned snapshot artifacts in full, the requirements and technical premises. The review hashes must refer to these exact snapshot bytes. Do not edit or canonicalize after capture. If any correction is needed, report it and return to authorship; an existing capture cannot be refreshed or its approval inherited.
5. Only after independent approval publish with publish-task-candidate.mjs and its exact review JSON. The public publication CLI requires explicit draft approval and rejects a changed draft, technical snapshot or stale digest. Read back official execution after confirmed publication. The visible documentary draft remains, but is not executable authority.

A failed capture/review preserves the original material. Never delete registry entries, approvals or snapshots to force reuse. Current write-once capture does not offer an automatic recapture/disposition command; report that boundary instead of claiming a corrected captured draft is approved. Both programmatic publication APIs and the CLI require the explicit exact-byte approval. A missing draft association never grants permission. Synthetic test fixtures establish their own clearly labeled fixture approval; production code has no legacy bypass.

## Purpose

Run PLAN for an absent official execution, or the bounded current REPLAN described below. One author produces plan.md, every active plans/slice-NN.md, tasks.md and every active tasks/slice-NN.md together. Do not implement or approve your preparation. Use the local templates and references/workspace.md. Requirements authority: sha256:<64hex> and Plan revision: <positive integer> bind the existing canonical requirements fingerprint and normative revision. Runtime delivery IDs do not establish acceptance.

### Domain guidance

For a technical change, inspect the native skill catalog descriptions and consult only the primary domain guidance and applicable specializations for the proposed scope. Use that guidance to shape boundaries, risks and checks; it does not expand requirements or authority. Administrative work and documentation without a product change do not load domain guidance by default.

## PLAN

Allocate a technical candidate using `node "<SKILL_ROOT>/runtime/prepare-task-candidate.mjs" --spec-path <SPEC_PATH> --operation <OPERATION>`. Keep its ownership marker. Create the editable draft as described above and render both Plan and Tasks there from UTF-8 template content as new writable files; do not copy frozen template modes. Fill semantic fields before serialization. Preserve rejected bytes and live authority. Before capture, a structural/editorial correction uses the same editable root and allocation. After capture, changes invalidate approval and require a fresh preparation, never an overwritten snapshot. A changed reviewed candidate never inherits its prior approval. Material scope/strategy changes return to authorship under the applicable requirements authority; do not allocate another root merely to fix format. If a change requires abandoning a registered allocation and no public disposition is admissible, preserve it and report the blocker rather than editing its registry or forcing CLOSE.

Write the observable delivery once and repeat it verbatim in the global Plan row, global Tasks row and detailed Task Result; keep richer explanation in the detailed Plan objective/strategy. Repeat Authorized Areas, Existing Inputs, Protected Responsibilities, Expected Tests and Verification Recipe consistently in the detailed pair. Dependencies contains only `- none` or one `- slice-NN` per declared predecessor; explanations belong in Risks and Strategy. Every requirement ID assigned in the global row, including R/AC/C IDs, needs an explicit obligation: mentioning an ID inside another obligation condition does not bind it. Do not infer missing obligations or silently replace conflicting authored content.

Plan carries objective, strategy, exact requirement IDs, serial dependencies, observable results, scope, exclusions and protected responsibilities. Tasks carry a useful Result, Acceptance Obligations with stable local IDs, an initial Checklist associated with those obligations, Expected Tests and the existing evidence/findings/attempt sections. Each obligation names the real requirement, complete or partial contribution, integral verification owner, observable condition and proof required. Never invent a requirement ID or claim full acceptance for partial work. Every condition has an integral owner and proof capable of observing it. A later integration slice cannot silently supply missing evidence for an earlier full acceptance.

Authorized Areas explicitly label `directory:` or `file:`. They define the permissible effects. Existing directories may remain broad areas, but do not grant unrestricted creation of future subdirectories. Under absent ancestors, declare every future leaf as an exact `file:` area; a future `directory:` area is unsupported. Expected Files and recipe product references do not replace this authorization. Preflight rejects declared outputs under missing parents without exact areas; unlisted future subdirectories are not thereby supported. Never create directories merely to pass preflight. Expected Files are operational predictions and may be future files. Existing Inputs must be present regular files when required. Changed/tested files are real files or explicitly proved removals; directories cannot stand in for hashes. Before serialization, all typed claims use their logical artifact location. Persist artifact-relative paths only, with one physical basis, containment and symlink guards. Auth, persistence and public-contract responsibilities are normative; path membership alone does not authorize their alteration.

Before approval, check cross-slice observation using [compact proof scope](references/compact-proof-scope.md). Prefer exact `file:` outputs over convenience-wide shared directories only after concrete inspection of verifier imports/configuration supports that boundary. Keep shared read-only dependencies in Existing Inputs. Globs, membership, mutable databases and unknown inputs do not become independent through script hashes or declarations. Retain conservative coverage and block unsupported proof claims. Plan the unique integral owner and finished-product terminal proof at the end of the queue. Existing broad plans remain conservative; narrowing requires normal authorship, user approval and independent review, never rewriting historical evidence.

`Requirements source` binds documentary authority; it is not an operational input catalogue. Reading a document to understand requirements does not make it an Existing Input. Declare actual product/check dependencies and deliberate read-only observation inputs there, not a bibliography of consulted documents. The canonical authority file and execution controls cannot be operational claims, even as read-only inputs or recipe references; an Authorized Area cannot contain them. Preserve the authority binding in `Requirements source` and legitimate observation inputs. Do not infer this boundary from filenames or forbid every file beside a SPEC.

Declare the normative Verification Recipe identically in detailed Plan and Task using [the recipe contract](references/verification-recipe.md). Select executable, execution base, typed file arguments and reviewed indirect dependencies explicitly. External references must bind Existing Inputs; product references require Authorized Areas. Run the existing serializers before review. Inputs provide read/capture coverage and never authorize writing. The reviewed recipe reaches the runner and its receipt.

Expected Tests and obligation proofs remain explanatory prose and do not define the mechanical domain. Do not infer inputs from punctuation, quotes, filenames or filesystem homonyms. The official producer records each newly created preparation under the execution initialization lock in the per-execution registry outside the candidate before returning it. Keep its marker; never edit the registry or adopt an unrelated root. Genuine stale candidates remain classified, but stale source/CAS blocks their use.

The capture command runs prepare-plan-candidate.mjs and serialize-plan-paths.mjs internally. These shared producers prepare both sets, bind delivery IDs and validate the complete candidate before explicit approval. No MATERIALIZE_TASKS or REVIEW_TASKS operation exists. The absorbed producers are mechanical resources, not another cognitive phase.

Keep the technical capture isolated and the single editable draft beside SPEC. After explicit user approval, `publish-task-candidate.mjs --spec-path SPEC_PATH --candidate-execution-root CANDIDATE_EXECUTION_ROOT` without a review returns AWAITING_REVIEW and never installs the candidate. The current producer does not import or migrate incompatible preparations.

## Output

At AWAITING_REVIEW, report the exact isolated candidate root, source activation when present, current requirements authority, artifact paths and review request when returned by the producer to the caller, then stop and return control. The caller invokes REVIEW_PLAN in an independent context; do not start or delegate that next operation from PLAN or REPLAN. No implementation, formal validation or self-approval.

If the caller requests only re-delivery of an Initial handoff whose preparation remains unchanged, expose the complete literal preserved producer return as one JSON command output. Do not reconstruct it from a summary, rerun planning/preparation/publication, change artifacts or invoke REVIEW_PLAN. Report an absent or changed original instead of inventing a handoff; the caller still validates the allocation, authority and artifact hashes.

## REPLAN

The current producer supports three bounded set replacements under the same requirements authority. The source must be quiet, with every member inspected current/PASS and no normal handoff, except the exact authenticated offer of a first terminal judgment when all local proofs are current. That offer is not an active operation; stale integral proof, pending local work and unresolved ownership remain blocked. REPLAN still requires explicit authorization and independent preparation review. Q18 moves all active contributions to completed. Q19 starts with an empty active queue, keeps at least one contribution completed and reopens exactly one completed contribution without pending normalization for a private normative change. A consumer of the reopened contribution or a transverse change blocks this path. Q20 starts with an empty active queue whose contributions are current/PASS but whose integral proof is absent. It reopens exactly the same integral owner for terminal validation, preserving its full local normative contract and local revision. Other replacements remain unsupported; preserve the source and report the runtime diagnostic.

After preflight, allocate with `node "<SKILL_ROOT>/runtime/prepare-task-candidate.mjs" --spec-path <SPEC_PATH> --operation REPLAN --completed-delivery-ids '<JSON_ARRAY_OF_COMPLETED_UUIDS>'`. Supply the exact source UUIDs that will remain completed. For an explicitly requested Q20 terminal reentry, add `--terminal-validation true`; the selected integral owner may be the sole contribution, with `[]` remaining completed. The official allocation captures the source activation, physical tree and preparation revision under the common lock; a pending registered REPLAN blocks another allocation. Keep the returned root and marker. Never edit the registry, adopt another root or use Initial to replace execution.

Author the current global Plan/Tasks and each reopened detailed pair from the current normative leaves and local templates. Do not restore deleted detailed artifacts from an old preparation. Preserve global objective/strategy/risks, requirement IDs, dependencies and integral owner identities. Q19 permits only a private change in Existing Inputs, Risks and Strategy, Expected Tests or Verification Recipe, subject to the existing shared-input/output guards. Operational checklists and Expected Files cannot expand that authority. Use the same prepare-plan-candidate and serialize-plan-paths commands as PLAN. The producer derives source UUIDs, preparation revision +1 and the reopened local revision +1; it preserves completed local revisions, counters, baselines and slice high-water. Q20 increments only the preparation revision: preserve the same local revision, recipe, inputs, authority meaning and all retained records/objects. Do not invent a private delta to enter terminal validation.

Propose without a review first and pass the exact returned review request to the independent reviewer. Retained records and objects remain literal. Canonical owner representation can change current indices/envelopes for more than the reopened member; review the resulting evidence hashes without inventing independence or changing the owner UUID. Q18 requires exact retain-current decisions; Q19 retains completed contributions and requires revalidate for the reopened contribution. Its old PASS remains historical until another legal VALIDATE_SLICE, with no reset or new validation performed by REPLAN. Q20 requires retain-current for the reopened owner as well: review the exact final Task/index and evidence digest after any canonical owner index change. It reads back local PASS/current with a VALIDATE_SLICE handoff and terminal diagnostic; the next formal dispatch must explicitly request terminal judgment. REPLAN itself does not produce integral PASS or COMPLETE.

Publication uses the exact independently reviewed candidate and existing CAS/product/requirements guards. On an interrupted replacement, preserve the returned publisher allocation and use `node "<SKILL_ROOT>/runtime/publish-task-candidate.mjs" --spec-path <SPEC_PATH> --recover-allocation <PUBLISHER_MARKER>` for official recovery. Confirm publication and own cleanup separately; do not replay publication, take over an uncertain lock or delete foreign controls. Recovery does not run an agent or recipe. Read back the legal handoff; neither an empty active queue nor retained local PASS grants COMPLETE or terminal acceptance.

## Minimum Reads

Current requirements and exact declared IDs, relevant current proof, all four templates, and code only for decisive decomposition premises.

## Allowed Effects

Complete isolated Plan+Tasks candidate; publication occurs only after independent exact-byte review through the current producer. An empty Task alone never proves pristine: inspect known owners, operations and actual captured product first.

## Blocks

Missing decision, stale requirements/base, incompatible legacy, ambiguous carriers, lost history, ownership conflict or unsafe path.
### Authenticated stale completed contributions

A completed proof with `EVIDENCE_STALE` observation drift is historical, not corrupt or current. The explicit reviewed completed-revalidation flow is the sole exception to the current/PASS preparation-source requirement above. Follow `references/completed-revalidation.md`: name every stale completed UUID, preserve all contracts and historical sources, obtain fresh user capture approval and independent review, and require new local and terminal judgments. Generic preflight stays strict. Never delete controls, rewrite evidence, use `retain-current` for reopened contributions, or run RECONCILE to bypass this gate.
