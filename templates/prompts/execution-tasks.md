Para cada caminho concreto em `expected areas`, normalize `SPEC_PATH` com a authority exportada `resolveExecutionWorkspace(SPEC_PATH)` de `runtime/execution-state.mjs`, use o `executionRoot` retornado e não derive o execution workspace em paralelo. Defina `taskPath = path.join(executionRoot, "tasks", "slice-NN.md")`; resolva a referência aprovada a partir do artifact que a declarou para obter `physicalTarget`; depois recalcule o claim como `path.relative(path.dirname(taskPath), physicalTarget)`, normalizado para `/`. Não copie, encurte nem ajuste por texto o caminho do plan; `execution/`, `plans/` e `tasks/` são bases diferentes. Candidate validation deve rejeitar bases inválidas sem fallback ou autocorreção.
Os code spans `Likely Areas` dos detailed plans aprovados são as seleções semânticas. Antes de invocar candidate validation, execute o serializer determinístico em `__MATERIALIZER_TASK_PATH_SERIALIZER__` contra o `SPEC_PATH` exato e o candidate isolado:

`node "__MATERIALIZER_TASK_PATH_SERIALIZER__" --spec-path "{{SPEC_PATH}}" --candidate-execution-root "$CANDIDATE_EXECUTION_ROOT"`

O serializer deve gerar todos os code spans `expected areas` das tasks a partir dos targets físicos do detailed plan e do diretório da task final. Se sair com erro, retorne `BLOCKED` sem invocar candidate validation nem publicar; nunca espere a validação rejeitar, corrija depois da rejeição, adivinhe um target ou edite artifacts live.
O publisher executa esse mesmo serializer determinístico novamente imediatamente antes da validação estrita do candidate. Trate essa passagem do publisher como a boundary mecânica final; nunca copie para a task um claim relativo ao plan nem dependa de um caminho escrito pelo modelo sobreviver à publicação.
Antes de criar ou editar qualquer task, obtenha a raiz candidata com o helper determinístico `__MATERIALIZER_TASK_CANDIDATE_PREPARER__`: `CANDIDATE_EXECUTION_ROOT="$(node "__MATERIALIZER_TASK_CANDIDATE_PREPARER__" --prepare --spec-path "{{SPEC_PATH}}")"`. Use exatamente essa saída absoluta em todos os writes, no serializer e no candidate validator; não derive, encurte, substitua ou reconstrua a raiz. O helper cria uma cópia completa e isolada do `executionRoot` vivo, preservando `plan.md`, todo `plans/slice-NN.md`, `tasks.md`, `references/` e qualquer task histórica autorizada; não crie um candidate contendo somente `tasks/`. Na materialização inicial, crie as novas tasks e o índice somente depois dessa cópia completa. Candidate validation exige esse execution tree completo antes da publicação.
Depois que o serializer sair com zero, publique somente pela boundary determinística `__MATERIALIZER_TASK_CANDIDATE_PUBLISHER__`: `node "__MATERIALIZER_TASK_CANDIDATE_PUBLISHER__" --publish --spec-path "{{SPEC_PATH}}" --candidate-execution-root "$CANDIDATE_EXECUTION_ROOT"`. Ela reutiliza o validator oficial antes de publicar, rejeita alterações fora de `plan.md`, `plans/`, `tasks.md` e `tasks/`, copia bytes para arquivos regulares independentes e faz o readback estrito antes de confirmar. Se sair diferente de zero, retorne `BLOCKED` sem nova tentativa. Não use `ln`, `cp -al`, hard links, cópia direta ou `mv` manual para escrever o executionRoot live; não publique parcialmente nem corrija depois da rejeição.
Antes de validar o candidate, leia `templates/tasks.template.md` e copie sem alteração o bloco completo `# File Purpose Header` para `execution/tasks.md`: os sete campos ordenados, seus valores, `owner: stnl-task-materializer` e `status: ready` são autoridade estrutural. Gere cada `tasks/slice-NN.md` a partir de `templates/slice-tasks.template.md` preservando seu File Purpose Header completo. Se qualquer header estiver ausente, truncado, reordenado ou alterado, repare o candidate antes da validação; nunca publique um índice parcial.
